# ADR-042: the pinned image, SeedVR2's weights and VAE, and guarding the agent on binc-pc

**Status:** Partly built 2026-11-15 (the pin); the rest is proposed, with the open questions below.
**Context from:** Lucas ("bincs agent keeps bypassing our system"; "bincs agent says our key is unauthorized"; "can't we rebuild and pin image"; "seedvr2 is in comfy org isn't it?"; "can we use a dedicated volume on runpod for these weights"; "to stream them to the volume on build?"; "we also need to be able to choose vae"; "doc these issues").

## 1. The image tag moved (built)

`contract-v26` is re-pushed by every rebuild; it moved on 2026-11-14 at 20:58 UTC (digest `a06a461c…`, replacing the 19:04 and 19:05 builds), so pods created a day apart could run different contents. Fixed in ADR-020's amendment: `mounts.DEFAULT_IMAGE_REF` and the Default Configuration are the digest, `gpus.CU13_PINS` pairs it with the CUDA 13 digest (`116c2012…`), and the workflow tags `<variant>-<commit>` and prints the digest. **Open:** the merge, a release carrying the new default, and telling Binc the digest and what the 14 Nov rebuild changed (the commits after `7e1e94e`: round-nodes.sh, no workflow seeding, the converter's browser path).

## 2. "Our key is unauthorized" (diagnosed, not reproduced)

Checked from this Mac on 2026-11-15: the RunPod key works (balance returned), the BH bucket keys list ten rounds, and last night's pod pulled the private image, so the `ghcr.io` login worked then. Not set here: the Anthropic key. The agent that reported it is on **binc-pc**, which has its own config, so the likely causes are a missing or different key there. **Open:** the exact error text from binc-pc. `AccessDenied` is the bucket, `401` the RunPod key, `denied: access forbidden` the registry login (Registry auth ID in Default Configuration), `authentication_error` the Anthropic key.

## 3. Binc's agent goes around the system (guard written, not wired)

The spend gate (`approved_by`, USD 100) lives only in the pod-manager MCP. A shell can reach the same things (`runpodctl`, RunPod's REST/S3 endpoints, `start.sh pod create`, `aws s3 rm` on BH's bucket, writes into `projects/desktop/`), and `.claude/settings.json` has only an Edit/Write hook and no permissions. `.claude/hooks/guard-bash.sh` blocks those routes and names the MCP tool to use (tested on twelve sample commands). **Open:** register it in `.claude/settings.json` with a `Bash` matcher plus a `permissions` block, ship it to binc-pc through `shared/governance/` (nothing here reaches that machine), and get one real example of a bypass to see whether the cause is routing, stale docs, context or settings.

## 4. SeedVR2 (decided in part)

- The **nodes are in ComfyUI itself** (`comfy_extras/nodes_seedvr.py`, `comfy/ldm/seedvr/`) at the commit the image pins (`3c1b7a17…`): no node pack to add. The `FalAPI_*seedvr*` nodes in `ComfyUI-fal-API` are a cloud API and need no weights.
- The **weights are in no image and in no folder on this Mac**; the two volumes (`a3upg9ey48`, EU-RO-1; `kceera10qh`, EUR-IS-2) were not listed. Model size (3B or 7B, fp16 or fp8) is not chosen, and no graph of Binc's uses SeedVR2.
- **Where they live:** on the volume under `/workspace/comfy-shared/models` (`diffusion_models/`, `vae/`), about 7 to 16 GB, USD 0.07 per GB per month. Not baked into the image (7 to 16 GB on every pod pull). A pod mounts one network volume only, and only one in its own datacenter, so a "dedicated weights volume" cannot sit beside the workspace volume: the options are the workspace volumes themselves, or a master copy that Clone copies per datacenter.
- **Putting them there:** a build cannot write to a volume (the runner mounts nothing). RunPod's S3 API can, from any machine with no pod, but only in S3 datacenters: EU-RO-1 is one, EUR-IS-2 is not in `S3_DATACENTERS` (the list has `EUR-IS-1`; check RunPod's current list). It needs RunPod S3 keys as GitHub secrets, which do not exist yet. Otherwise a short pod runs one download (cents, any datacenter). Proposed: a separate manually triggered workflow or a small script with a manifest (file, URL, sha256, destination), idempotent, size-checked; not part of the image build.

## 5. Choosing the VAE

ComfyUI lists every file in `models/vae` in its VAE loader, and it recognises SeedVR2's VAE by its contents (`comfy/sd.py`: the `decoder.up_blocks.2.upsamplers.0.upscale_conv.weight` key), not by name. So choosing a VAE needs no code in the image: it is whichever files are on the volume. The weights manifest should therefore list **every** VAE we want selectable, not one, and a graph picks by file name. **Open:** which VAE files (the SeedVR2 one, and any others for other graphs), and whether the app should show what is in `models/vae` on the volume (Browse already lists folders).

## 6. Built 2026-11-15: a model choice per pod

`libs/core/src/podmodels.ts` keeps, per pod (`pod-models.json`, dropped with the pod), a **VAE** (`VAELoader.vae_name`) and a **diffusion model** (`UNETLoader.unet_name`). `runflows.run` puts the choice into each converted graph that has exactly one loader of that class; with two or none it leaves the graph alone and names it in the result (`models`). `runflows.models(pod)` lists the files the pod's ComfyUI offers (`/object_info/<loader>`), so whatever is on the volume can be picked and **nothing is baked into the image or downloaded by the app**. MCP: `pod_models` (read, and set with `vae` / `diffusion_model`; empty clears). Tests: `libs/core/tests/podmodels.test.ts`. **Defaults travel:** the Default Configuration has `models` (`vae`, `diffusion_model`; Default VAE / diffusion model fields in the window), used by every pod without its own choice (`podmodels.effective`); it is in the *Pod defaults* section of the configuration export and import (ADR-023). The per-pod choices are not exported (a pod id means nothing on another machine; listed in `NOT_EXPORTED`). The S3 keys and the pinned `image` already travel (the *Keys and tokens* and *Image* sections). **Not built:** the per-pod picker in the Run workflows window, and the weights manifest and download script.

## 7. Where the weights go: all of them, on the volume

Every variant (3B and 7B, fp16 and fp8, and the VAEs) is kept on the volume under `models/`, about 35 to 45 GB (estimate, not measured), roughly USD 2.50 to 3 a month; each pod chooses at run time (section 6). Not streamed at run time (a billed pod waits for the download, and Hugging Face may refuse it); not baked into the image. The S3 route needs RunPod S3 keys: Settings, S3 API Keys in the RunPod console, then Default Configuration's S3 fields (or the Add S3 keys button in the volume browser). **Update:** S3 keys added 2026-11-15 and proven (a free listing of `a3upg9ey48`); the volume holds 89 GB of 250. Files, from `Comfy-Org/SeedVR2` on Hugging Face (Apache-2.0): `diffusion_models/seedvr2_3b_fp16` 6.78 GB, `seedvr2_3b_fp8_e4m3fn` 3.39 GB, `seedvr2_7b_fp16` 16.48 GB, `seedvr2_7b_fp8_e4m3fn` 8.24 GB (each `.safetensors`), and `vae/seedvr2_ema_vae_fp16.safetensors` 0.5 GB. They stay on the volume, mounted into pods, not in the image (the registry's 10 GB layer limit would also stop the 7B fp16). **Open:** the transfer: from this Mac over the S3 API (no spend, but the uplink is the limit) or by a short pod downloading directly (cents, fast, needs a named yes). Previously: free space on `a3upg9ey48` (it holds rounds), a named yes for the pod or the transfer, and the exact file names from the official template.

## 8. What the SeedVR2 files are

SeedVR2 is a video and image upscaler. ComfyUI has its nodes built in (`comfy_extras/nodes_seedvr.py`: `SeedVR2Preprocess`, `SeedVR2Conditioning`, `SeedVR2TemporalChunk`, `SeedVR2TemporalMerge`, `SeedVR2PostProcessing`); only its **weights** are missing from the image, and they are kept on the volume, never in the image. Source: Hugging Face `Comfy-Org/SeedVR2` (Apache-2.0). Sizes as listed there on 2026-11-15.

| File | Goes in | Size | What it is |
|---|---|---|---|
| `seedvr2_3b_fp16.safetensors` | `models/diffusion_models/` | 6.78 GB | The upscaler network, 3 billion parameters, full 16-bit precision. The safe default. |
| `seedvr2_3b_fp8_e4m3fn.safetensors` | `models/diffusion_models/` | 3.39 GB | The same, 8-bit: half the size and memory, slightly lower quality. |
| `seedvr2_7b_fp16.safetensors` | `models/diffusion_models/` | 16.48 GB | 7 billion parameters, 16-bit: the best quality, the most VRAM. Over the registry's 10 GB layer limit, so it could not be baked into an image anyway. |
| `seedvr2_7b_fp8_e4m3fn.safetensors` | `models/diffusion_models/` | 8.24 GB | 7 billion, 8-bit: near the 7B quality in about half the memory. |
| `seedvr2_ema_vae_fp16.safetensors` | `models/vae/` | 0.5 GB | The VAE: encodes frames into SeedVR2's latent space and decodes the result. Every SeedVR2 graph needs it, whichever network is chosen. ComfyUI recognises it by its contents, not its name. |

A graph uses **one** diffusion model and **one** VAE. Which ones a pod uses is the pod's choice (section 6), so having all four on the volume costs only storage (about 35 GB, USD 2.50 a month); nothing is loaded into a pod's memory until a graph names it. The Comfy-Org repack also has `sharp`, int8, mxfp8 and nvfp4 variants of the 7B and 3B networks; they are not fetched.

Status 2026-11-15: the VAE is on `a3upg9ey48` (`comfy-shared/models/vae/seedvr2_ema_vae_fp16.safetensors`, 478.1 MiB, uploaded over the S3 API at about 2.5 MB/s); the four networks are not yet (approved by Lucas for a short pod; the Mac's uplink would take about four hours). The 110 to 124 byte files already in `diffusion_models/` and `vae/` are placeholders, not weights.

## 9. Shared: the Volumes and Models windows, and the Shared volume

Lucas: "instead, call this Shared, and clicking it allows user to choose volumes or models each have their respective modals"; "under models, we should be able to search hugging face repos and choose the model we want ... and load that into our shared volume"; "shared volume should also show up under network volumes, it should be NOT deleteable though and have a shared badge".

- **The nav button** that said Volumes says **Shared** and opens a chooser with two cards: **Volumes** (the existing window, unchanged) and **Models** (new). Other places that open Volumes directly (the pod card's volume link, the configuration's Add volume, the pod form) still do.
- **The Shared volume** is the one that holds the shared models: a Default Configuration setting `shared_volume_id` (account-specific, in the *Volume and datacenter* section of the export and import). It is chosen in the Models window; until one is chosen the models go to the Default Configuration's volume. The Volumes list marks it with a **Shared** badge, its Delete is disabled with the reason, and the core refuses it too (`volumes.remove`: "is the Shared volume"), so an agent through `delete_volume` cannot delete it either. Choosing another Shared volume, or none (`volumes.setShared('')`), frees the old one to be deleted.
- **Models window:** search Hugging Face (`hf.search`: public API, no key), open a repo to see its weight files with exact size and sha256 (`hf.files`), choose files and a destination folder (guessed from the path, changeable), and load them onto the Shared volume. The window also shows what the volume already holds under `models/` (free over S3 when keys are set).
- **Loading is a pod job** (`podpull.fetchModels`, kind `fetch`): a short pod, or your own pod on that volume, downloads straight into `comfy-shared/models/<folder>/` (resumable, size-checked, then sha256-checked against Hugging Face's value; a file already there at the right size is skipped; the pod is deleted at the end). It **spends the pod's minutes**. **No approval is asked for**: it is Lucas's own volume and account, and the models are not Binc's material, so their policy does not apply. `approved_by` is optional everywhere, in the window and in the MCP tool; if given, the job's log records it. It is refused while another job runs on the volume. It always uses a pod, never the S3 API, because the download has to happen on the datacenter's side of the uplink.
- **What a request can ask for is fixed in the core** (`hf.resolve`), not by the window: the repo and path are looked up on Hugging Face again, so the URL, size and hash are Hugging Face's, never the caller's; only `.safetensors`, `.gguf` and `.pth` files; the folder is one of `diffusion_models, vae, checkpoints, loras, text_encoders, clip, clip_vision, controlnet, upscale_models, embeddings`; at most 20 files at a time; no `..`, no unusual file names. Gated and private repos answer 401/403 and are refused with the reason (a pod has no Hugging Face login). `.pth` files are pickles in principle; ComfyUI loads them with `weights_only`, and they are limited to upscaler-style files by the same allow-list, but a repo you do not trust is still a risk: read the repo before you load from it.
- **MCP:** `models_search`, `models_files`, `models_fetch` (no `approved_by` needed), `set_shared_volume`. Same core calls as the window.
- **Status 2026-11-15:** built: the core (hf.ts, the `fetch` job, `podpull.modelsOnVolume`, `shared_volume_id`, the delete refusal), the Shared button and its two windows, the IPC `models` namespace and `src/api/models.js`, the MCP tools, and the tests. The agent rules (named yes, ceiling) are system-wide settings in the app's settings file, exported and imported as their own section (*Agent rules (system-wide)*), never part of a pod's configuration. The SeedVR2 files are the first thing to load through it (section 8).

## 10. The agent shell guard (a setting)

Lucas: "a bash script / PreToolUse hook for Bash that stops agents freelancing, as a setting under Connect > MCP, included in import/export".

- **What it is:** a Claude Code `PreToolUse` hook for `Bash` (`.claude/hooks/guard-bash.sh`, shipped in the core as `agentguard.SCRIPT`, byte-identical to the repo file; a test asserts it and `node scripts/gen-agentguard.mjs` regenerates the constant). It reads the command from the hook's JSON on stdin and exits 2, with the way back, for: `runpodctl`; direct calls to RunPod's REST, GraphQL and S3 endpoints; the pod CLI's `create`, `resume`, `recreate` and `delete`; mutating `aws s3` calls on BH's bucket; shell writes into `projects/desktop/` (rm, mv, tee, `>` and a `cp` into it, sed -i, git add). Reads, `ls`, `aws s3 ls` and `cp` out of the mirror pass.
- **It is a heuristic, not a sandbox.** It matches command text, so a determined agent (or an unusual spelling) gets round it; it catches the common bypasses. The real boundary stays the pod manager's own rules and the MCP.
- **The setting is system-wide** (`AGENT_SHELL_GUARD` in the app's settings file, `agent_shell_guard` in `settings.get()/set()` and `set_settings`), with the agent rules in section 6 of the same family. Switching it **on** writes the script to `<config folder>/hooks/guard-bash.sh` (mode 755) and adds ONE entry `{matcher: "Bash", hooks: [{type: "command", command: <that path>}]}` to the **current OS user's `~/.claude/settings.json`** (created if absent); switching it **off** removes only that entry (and its group if ours was the only hook in it). Other keys and other hooks are never touched; our entry is recognised by its command path; installing twice is a no-op. The file is **backed up first** to `<config folder>/backups/claude-settings-<timestamp>.json`; an existing file that is not valid JSON is refused with a message and nothing is changed (the setting is then not left on).
- **Per-user scope:** `~/.claude/settings.json` applies to every project of that OS user, not only this repo. A project's own `.claude/settings.json` is not edited. On binc-pc the switch has to be turned on in the app (or the configuration file imported) while logged in as the user whose Claude Code runs the agent.
- **Status:** `agentguard.status()` gives `enabled` (the setting), `installed` (our entry is present and the script exists and is executable), the settings file and the script path; over IPC `agentguard.status/set`, in the MCP `agent_guard_status` (read) and `set_settings agent_shell_guard`. It is part of the `governance` section of the configuration export (`governance.shell_guard`): importing that section installs or removes the hook, and undo restores it.

## 11. What travels in the configuration export

The export (ADR-023, amended 2026-11-15) carries what this ADR adds: the Shared volume id (*Volume and datacenter*), the default VAE and diffusion model (*Pod defaults*), the agent rules and the shell guard (*Agent rules (system-wide)*), and, with the other connections, the console URL (*MCP connections*) and the repositories and accounts (*Repositories and accounts*). Per-pod model choices and pod attachments are pod-bound and are not exported.

## 12. The wanted-models list (built 2026-11-15)

Lucas: "when importing and exporting settings, keep a copy of the names of the models, so we can import. these models can then be loaded onto a shared volume in any datacenter."

1. **What it is.** A list in the Default Configuration (`wanted_models`, libs/core `wanted.ts`): per entry the models folder (one of the ADR-042 folders with at most one sub-folder), the file name, the Hugging Face repo and path (and revision), the size, optionally the sha256 and a note. Names and coordinates only, never weights; tied to no volume, account or datacenter. An entry with no repo (a file recorded from a volume that no repo is known for) is listed but cannot be loaded. Entries are checked like a fetch is (`hf.isFolder`, repo, safe path, safe name); merged by repo, path and folder.
2. **In the export.** Its own section, *Wanted models*, key `wanted_models`: on import the incoming entries are merged into the list (what is here stays; the plan shows whether anything is new). Undo restores it with the rest of the configuration. Nothing in it is machine- or account-specific.
3. **Filling it.** In Shared > Models: *Add to wanted list* beside Load on a repo's files; *Saved List* (the weight files over 1 MB on the volume, over S3, with the repo of an entry already listed kept); *Install Defaults* (reads `comfy-shared/models/_canalv2_pull/MODELS_PULL_v003.csv` off the volume over S3, or pasted CSV text when the volume cannot be read that way; rows whose destination is not a models folder, like `depth_anything_v2_vitl.pth` into controlnet_aux's ckpts, are skipped and counted).
4. **Loading it.** Each row says *on the volume*, *missing* or *not checked* (the volume cannot be listed without S3), by folder, name and size (within 2%). *Load Missing* sends every missing entry that has a repo through the same Hugging Face fetch as Models: a short pod, resumable, sha256-checked, gated repos refused. A volume runs one job at a time and a job is at most 20 files, so the first job is started and the core starts the next as each finishes, stopping at the first that fails. The answer says the file count and GB, and warns when the models alone would not fit the volume (rounds on it are not counted, so that is the least it needs): resize first. Any Shared volume in any datacenter can be filled from the same list.
5. **MCP.** `models_wanted` (the list; with a volume, each row's state and the totals), `models_wanted_add` (entries, CSV text, or from `binc_list` / `installed`), `models_wanted_remove`, `models_load_wanted` (spends: the named yes when that setting is on, as for the other spend tools).
6. **Not done.** The list is not matched against what an installed file's repo was when the file was fetched before this section (such files are recorded with no repo until added from Hugging Face or Binc's list). Verified by tests with fake S3 and fake jobs; not run against a real volume or Hugging Face.

## 13. The default card (built 2026-11-15)

Lucas: "set pro 6000 as default card".

1. **One system-wide setting.** `default_gpu` in the Default Configuration: a key of the card table (`gpus.ts`) or `auto` (the cheapest card in stock). Default `rtxpro6000`. Not per pod: a pod's own configuration carries the field like any other, but the setting is shown once, in Default Configuration > Options, and travels in the *Pod defaults* export section.
2. **Where it applies.** A pod created with no card named (`pods.plan`: `req.gpu || cfg.default_gpu`), MCP `create_pod` when `gpu` is omitted, the create form's initial card (a card nobody picked follows the setting when it loads or changes; a picked one stays), the Queue's pool when a shot has no card (it was a hard-coded H100: `queue.poolGpu()`), and the card menu's `default`. An explicit card always wins; `pull_any_card` is unchanged.
3. **CUDA 13.** The RTX PRO 6000 needs the CUDA 13 image: the existing pairing picks it (a tag gets `-cu13`, a pinned digest its CU13_PINS pair, and the pod gets the CUDA 13 host filter), tested in `defaultgpu.test.ts`. The pin still names the 15 Nov images that predate the OCIO, LTX and Binc DPX packs until the CUDA 13 build of the new image is pinned.
4. **Out of stock.** The default card is treated like an explicit one: when RunPod has none in the datacenter the create fails with the list of what was tried; nothing silently picks another card. Choose `auto` to take whatever is cheapest.
5. **MCP.** `get_configuration` shows `default_gpu`; `set_configuration` takes it in `patch`.

## 14. The Hugging Face token and gated repos (built 2026-11-15)

Lucas pasted the app's error "black-forest-labs/FLUX.2-klein-9b-fp8 has no weight file flux-2-klein-9b-fp8.safetensors" and said "fix this".

1. **Cause.** The repo is gated (`gated: auto`). Without a token Hugging Face's tree API still lists the file but masks its `lfs.oid` as asterisks, and `/resolve` answers 401. `hf.files()` kept only files with a 64-hex oid, so the file vanished and `resolve` reported a missing file: the wrong reason.
2. **A secret setting, `HF_TOKEN`** (`hf_token` in `set_settings`): stored with the other keys in the settings `.env`, shown as the last four characters only, in the Default Configuration (Keys), in the export's `secrets` section when secrets are included, and in the MCP `get_settings` and `set_settings`. System-wide, not per pod. The hint in the window points to huggingface.co/settings/tokens (read access) and says the repo's terms must also be accepted on its page with the same account.
3. **hf.ts.** With a token every call to huggingface.co carries `Authorization: Bearer <token>` (only to huggingface.co; never logged, never in an error). A file whose hash is masked is listed with its name and size and `locked: true`; `resolve` refuses it with a 403 that says what to do: without a token, "<repo> is gated: accept its terms on huggingface.co and set a Hugging Face token (Default Configuration)"; with a token, that the token's account has not accepted the terms. A 401 or 403 from the API itself is said the same way. The window shows a gated badge on such files and keeps Load disabled for them (Add to wanted list still works: naming a file for later is not downloading it). Wanted-list loading goes through the same lookup, so a token makes gated repos load and no token refuses them with the clear message.
4. **On the pod.** The token reaches the pod only on ssh's stdin, in the script: one line writes it to a curl config file under `/dev/shm` (RAM, mode 600, removed by a `trap` when the script ends), and curl reads it with `-K`. It is never on a command line or on the volume. curl follows Hugging Face's redirect to its CDN with `-L` (never `--location-trusted`) and `--proto-redir =https`, so the Authorization header is dropped when the host changes. Everything the pod prints passes the same redaction as the S3 keys, so a token echoed by mistake is stored as `***` in the job's lines, its record and the History.
5. **Not tested live.** No real token was available: a fetch of a gated repo with a real token and an account that accepted its terms is unproven. The tests cover the header, the masked-hash detection, the messages, the script's text and the redaction, with fake Hugging Face answers.

## 15. Deleting model files from a volume (built 2026-11-15)

Lucas: "Already on the volume models should be able to be deleted too."

1. **In the window.** Shared > Models, "Already on the volume": a checkbox and a trash icon per file, and a *Delete selected (n, size)* button. The app asks first, with what and how much and the file names ("Delete 3 files, 46 GB, from comfy-workspace? This cannot be undone."); No changes nothing. Files of the `_canalv2_pull` folder (Binc's pull list and scripts) are bookkeeping and get no Delete.
2. **In the core.** `podpull.deleteModels(volumeId, items, { confirmed })` with items `{ folder, name }` as `modelsOnVolume` reports them: a folder directly under `comfy-shared/models/` (any that exists, not only the ones Hugging Face loads go to) and a name under it, sub-folders allowed. It refuses without `confirmed: true` (400), a path with `..`, an absolute path, a glob or shell character, a leading dot, the `_canalv2_pull` folder, an empty list and more than 200 files; the checks run before any pod or S3 call. It is refused (409) while another job runs on the volume, as a Hugging Face load is. Only the named files are removed, never a folder or a prefix.
3. **How.** Over RunPod's S3 API when the volume's datacenter has it and the keys are set: one `aws s3 rm s3://<volume>/comfy-shared/models/<folder>/<name>` per file (an exact key, never `--recursive`), after one `s3 ls` of `models/` for the sizes: no pod, no cost. Otherwise a short pod, or yours on the volume, runs a script that rebuilds each path under `/workspace/comfy-shared/models`, refuses anything outside it, and `rm -f --` each file, printing `DELETED <folder>/<name> <bytes>` (`MISSING ...` for one that is not there) and `DELETE-DONE` (`DELETE-FAILED` on a refusal). A new job kind `delete-models`, on the same machinery as Erase and the Hugging Face load; the job carries `deleted` (each file with its bytes) and `freed_bytes`, and the History records the job with the files.
4. **The wanted list keeps what was deleted** (section 12): the row shows *missing* again and *Load missing* would fetch it back. Nothing is removed from the list.
5. **MCP: `models_delete`** `{ volume_id?, items, confirmed, approved_by? }`: `confirmed` must be true; `approved_by` only when the named-yes setting is on (as the other mutating tools). Follow the job with `volume_job`. The Electron/HTTP API is `models.delete(volumeId, items, confirmed)`.
6. **Not tested on a real volume.** The tests cover the checks, the S3 calls with a fake `aws` (exact keys, sizes, a missing file, a failure), the pod script's text and its markers, the busy refusal, and the window's flow with a fake API.

## 16. A download shows its progress, the Queue shows volume jobs, a lost pod is listed (amendment, 16 Nov 2026)

Lucas, with Load Missing running: "i don't see the models installing", "it just keeps spinning i don't see progress", "badge should show downloading if downloading", "i don't see any jobs in queue for this either", "make sure these status updates are realtime", "ucwords the starting: ComfyUI-Pull-vol-...". The `.part` file on the volume was growing while the window said only the first log line, and nothing in the Queue.

1. **The pod says where it is.** `fetchScript` runs each `curl` in the background and prints `FETCH-PROGRESS <bytes of the .part> <bytes in all> <name>` every 3 s, then `FETCH-VERIFY <name>` before the checksum (minutes for a 40 GB file). The job parser (`feedFetchProgress`, `fetchTotals`) folds them into the job view: `bytes_done` (finished files + the partial), `bytes_total`, `files`, a smoothed `rate`, and `fetch { file, index, count, file_done, file_total, eta_s }`. Progress lines are not kept in `lines` or the History (one `FETCHED` line per file stays).
2. **States that mean something.** `creating` (pod being created) -> `starting` (pod booting) -> `connecting` (new: SSH reached, script starting) -> `pulling` (first progress line: downloading) -> `verifying` (checksum) -> `done | failed | cancelled`.
3. **The window reads the list, not one id.** `stores/volumejobs.js` polls `volumes.jobs` every 1.5 s while the Models window or the Queue is open (and `App.vue` every 5 s for the badge). The job shown in Shared > Models is the live fetch or delete on the target volume, so it follows every change and a window opened later shows the running job. `VolumeJobView` shows the stage in title case (*Creating Pod*, *Pod Starting*, *Connecting (SSH)*, *Downloading File 2 Of 5*, *Verifying Checksum*, *Done: 3 Files Loaded*), the bar and *file i of n: name - X of Y GB (rate, ETA)*, with Cancel at the right of the row. Job lines are shown through `ucwords` (names such as `ComfyUI-Pull-vol-a3upg9ey48-1115` and paths are left exactly as they are); the stored text is unchanged.
4. **The badge.** A wanted model whose `<name>.part` is on the volume has the state `downloading` (with `downloaded` bytes): *Downloading 25%* while a download runs on that volume, *Partial 25% (Load Missing Resumes It)* when none does (an interrupted one). The same badge is on the `.part` row under "Already on the volume", which has no Delete. MCP `models_wanted` reports `downloading`.
5. **The Queue.** A *Volume Jobs* section lists fetch, delete-models, erase, clone and browse jobs with their progress and Cancel (after a confirmation); the nav badge counts them. MCP: `volume_jobs`.
6. **A job lost at a restart.** The jobs live in the app's memory, so a restart loses them while their temporary pod keeps running (and billing). `pull-pods.json` still names it: any temporary volume-job pod that no running job owns is listed in the Queue as *Interrupted (No Job)* with *Delete Pod* (after a confirmation; `podpull.dropInterrupted`, MCP `volume_jobs` with `action: drop`). Nothing is deleted automatically, and a download that was running keeps its `.part`, so Load Missing resumes it.

Tested with fake pod output (progress, verify, finished files, the job view at each step, no progress lines kept), the list and drop of interrupted pods, the badge states, and Playwright with a job that advances one state every 1.5 s. Not tested against a real pod's stream: whether `stat` of the `.part` during a resumed `curl -C -` reports the full size from the start (it does on Linux; the bar then starts at the resumed point).

## 17. A download survives dropped connections (amendment, 16 Nov 2026)

**What happened.** Lucas's Load Missing ran 35 minutes (16:56 to 17:31 UTC), put 25 of 39 files (190 of 307 GB) on the volume, then failed with "Could not reach the pod over SSH". The script ran in the foreground of one ssh session, so one drop ended the job, and the job's cleanup deleted the pod in the middle of a 10 GB file.

**Decision.**
- The download script is started once on the pod, detached (`setsid nohup`, its own session, output in `/tmp/volfetch-<job id>/log`, its pid and its exit status next to it). The start call is repeatable: it starts nothing if the run is going or has ended. The script and the Hugging Face token in it are written to RAM (`/dev/shm`, mode 700) and removed when it ends; nothing of it is on the disk.
- The app follows the log with short ssh calls every 3 seconds, from a byte offset it keeps (`followScript`: whole lines only; the exit status is read before the log, so an exit means the log read is complete). `ServerAliveInterval=15`, `ServerAliveCountMax=3` and a 40 second limit per call.
- A call that fails (exit 255, a spawn error, the limit) is retried with a growing pause for up to 10 minutes. The job says **Reconnecting (Attempt n)** and goes back to the download state when a call answers; the offset is kept, so no line is lost or repeated.
- If the pod stays unreachable for the whole budget the job ends **interrupted** and its pod is **not** deleted: the script is still downloading. The error says so. The pod is listed in the Queue's Volume Jobs as *Interrupted (No Job)* with **Reattach** and **Delete Pod**. If the script never started the job fails and the pod is deleted as before (nothing runs there).
- **Reattach** (also `volume_jobs` with `action: reattach`) follows the run again from the start of its log, so the bar and the file list are rebuilt, and finishes like any download (the pod is deleted at the end). The pod record keeps the run id and the files' names, folders and sizes (never URLs or the token) so a restarted app can do this.
- Cancel stops the script's whole process group on the pod, takes its script and any curl config out of RAM, and the pod is deleted.
- Only a download (`fetch`) is detached for now; delete, erase, clone and pull still run in one session.

**Not verified.** The scripts are tested as text and against a fake pod; they have never run on a real pod (`setsid`, `stat -c` and `/dev/shm` are Linux-only, so they cannot run on this Mac). The first real Load Missing with a deliberately cut connection is the test.

## 18. RunPod's request limit: one shared answer, a calm banner, never "no volume" (amendment, 16 Nov 2026)

Lucas, in the window: "There is no volume to load onto: set a Default Configuration volume or make one Shared." (his configuration had both set), then "the fuck". Cause, verified: RunPod answered `429 listing network volumes: rate limit exceeded for the hour window`. The Models window builds its target from the volume list; an unreadable list was an empty list, so it said there was no volume. The app itself, and the agent pollers running beside it, had used the hour's requests.

**What the app asked RunPod, per minute, with the window open (read from the code, `setInterval`s and call sites; before this change):**

| Caller | Every | RunPod requests |
|---|---|---|
| Pods store `load()` (list + stats) | 30 s, **5 s** while a pod is starting | 2 a minute, **12** while a pod starts |
| Credits (Stats) | 60 s | 1 |
| Create-pod form open: datacenters and cards | 60 s | about 8 to 14 (one availability query, one datacenter list and five price chunks, plus the stock query) |
| Models window open: what is on the volume and the wanted list | 6 s, each one looks the volume up (REST) | **20** |
| Queue tick with an import running | 3 s | up to 20 (the pods on the volume) |
| Idle sweep | 60 s | 1 |
| A volume job following its pod | a few seconds | a few |
| Agent pollers (`list_pods`, `volume_job`, `models_*` through MCP) | whatever the agent chose | 4 to 8 each |

A window left open on the create form and the Models window, with one pod starting, was about 50 requests a minute; with an agent polling it was well past that.

**Now:**
- **One answer, shared.** `ratelimit.cached` keeps one answer per call for a while and lets concurrent callers share one request: pods 8 s, one pod 3 s, volumes 15 s, a volume 15 s, the account 30 s, GPU stock and a datacenter's cards 60 s, datacenter availability and prices 120 s. A write (create, stop, resume, delete a pod; create, resize, delete a volume) drops what it changed. Cached only when the call goes to RunPod itself: a test that injects its own `fetch` is not cached unless it says `cache: true`.
- **Steady state, same situation:** list_pods at most 7.5 a minute (the 8 s answer), volumes 4, a volume lookup 4, credits 2, the create form's 120 s answer 3 to 7 instead of 8 to 14; the Models window's 20 become at most 4 because the six-second poll reads the cached volume; the Queue tick shares the pods answer. About 15 to 20 a minute where it was about 50. An agent polling the same call costs nothing extra inside the window.
- **429.** `ratelimit.noteLimited` reads the window from RunPod's words (minute or hour) and `Retry-After`: a minute window waits 60 s; an hour window waits 5 minutes, then one probe, and on another refusal 10, then 15. Every read waits (`guard`) while backing off; a write still tries and says so when refused. The first answer after the wait ends it. The last good answer of every cached call is served instead (stale, with its age) while RunPod limits; with nothing to serve the 429 is thrown with its window and the retry time.
- **The banner.** One line under the nav bar: "RunPod Is Limiting Requests (Hour Window); Showing What Was Known 7 Min Ago; Retrying At 09:30." It is read from the core's memory every 5 seconds and makes no request to RunPod. MCP: the `rate_limit_status` tool, and every object answer carries `rate_limited` while it holds (a list stays a list).
- **A volume is never "no volume" because RunPod would not list it.** The last volumes seen are kept on disk (`volumes-cache.json`), so a restart during a limit still knows the names and datacenters. `volumes.list`, `volumeInfo` and the job's volume lookup fall back to that record, then to the stored ids (name = id, the configured datacenter), marked `stale`. The Models window takes its target from the stored Shared or default id when the list failed; "There is no volume to load onto" appears only when no id is stored at all.
- **Test hygiene.** A full run of the core tests appended "imported from a file" and "restored from a backup" entries to the real `~/.config/runpod-pod-manager/history.jsonl` (`configio.test.ts` isolated the mounts file and the settings but not History). `tests/setup.ts` (vitest `setupFiles`) now points the config directory and Claude Code's settings at a scratch folder before any test; `tests/realconfig.test.ts` fails when any path the core writes would resolve inside the real directory. The MCP tests and the Electron specs already used scratch directories; the browser specs use a fake API.

Unproven: nothing was run against a real rate-limited RunPod; the answers are fake 429s. The call counts are read from the code, not measured on the wire.

## 19. Retry Later: a wait instead of a failure, for Resume and for Create (amendment, 17 Nov 2026)

Lucas, after a resume of `CanalV2-base-graphs-v001` (a pod made outside the app, an RTX PRO 6000, no network volume, a 200 GB container disk) failed with "There are not enough free GPUs on the host machine to start this pod", and a create of `CanalV2-lores-v003-a-v27` on an A100 SXM failed with "No card available right now": "Retry later - when clicking resume, have this be an option, let the user pick, or mcp", and then the same for creating a pod.

**The problem.** RunPod pins a stopped pod to the host it ran on; with no free GPU there the resume fails, and the only way on the app had was Recreate, which terminates the old pod **and its container disk**. For a pod with no network volume that is the loss of whatever is on the disk, and the pod was Binc's. A create has the same shape: a failure with nothing to do but ask again by hand.

**What it does.**
- A *watch* (`libs/core/src/podwatch.ts`, kept in `~/.config/runpod-pod-manager/pod-watches.json`, so it survives a restart) retries the same resume, or the same create request, every `every_s` (default 120, at least 60) up to `give_up_h` hours (default 12, at most 72). The app's timer (and an MCP server's, while it is up) looks for due watches every 15 s.
- Only "no free GPU" keeps a watch waiting, and the core now says so in a field, not just words: `CoreError.code` is `host_full` (a resume) or `no_card` (a create). A missing pod, a rejected key or a bad request stops the watch with the reason. RunPod's request limit (ADR-042 section 18) is waited out to the limiter's own time, never hammered. A dropped connection is not an answer: the watch goes on.
- **A create never makes a second pod.** The watch writes `creating` to its file *before* it asks RunPod and clears it only on a definite "no card". If the answer is lost (a dropped connection, a restart in the middle) the marker stays, and the next try looks for a pod with that name first and adopts it. Cancelling while a try was in flight says to check the pod list. Two watches for the same pod, or the same name, are refused.
- Two processes (the app and an MCP server) may both run the timer: a watch carries a short claim (pid and time) and the other waits it out; the by-name check is the second guard for a create.
- History: a successful watch records the normal `started` / `created` pod event with "pod resumed / created after waiting N min"; a watch that gave up, stopped or was cancelled is a `change` event in the new area `pod`.
- **Window.** After a Resume that finds the host full the card offers **Retry Later** beside Recreate (Recreate's confirm now says the pod and its container disk are deleted and points to Retry Later). A Create that finds no card shows **Retry Later** in the form's error. What is waiting, with its try count, next try and last answer, is listed above the pods with a Cancel, and what ended in the last 10 minutes stays there. The list follows the core every 6 s; the pod list refreshes when a watch ends.
- **MCP.** `resume_pod` and `create_pod` take `retry_until_free`, `every_minutes`, `give_up_hours`; without `retry_until_free` the answer says plainly that it is an option next to `recreate_pod`. `pod_watch {action: list|cancel, id|pod_id}` lists and cancels both kinds. `recreate_pod`'s description now says it terminates the container disk.

**Cost and consent.** A retry spends exactly what the same Resume or Create would; the watch adds no spend of its own beyond the pod it eventually starts (a started pod bills at once). The named-yes rule, when the setting is on, is asked once, at the `create_pod` call that registers the watch (the watch records it in the log line, not in the file).

**Unproven.** Built and tested with fake RunPod answers (core, MCP, browser); not yet run against a real full host or a real out-of-stock create. The label of a resume watch is read from the pod's details at registration, which is one extra RunPod call.

**Amendment 2026-11-17: Retry Later asks what to wait for.** Pressing Retry Later no longer starts the watch at once: a popup (`RetryLaterModal.vue`) names the pod, its datacenter and the schedule (every 2 minutes, up to 12 hours) and offers two options, **Same GPU: <model>** (the first, default: the resume watch of before) and **Another GPU in <datacenter>** (a list of the cards that datacenter runs, free ones first then by price; one out of stock stays choosable because the create watch waits for it; a card outside the app's table is not offered). "Start waiting" is disabled until the choice is complete. Another GPU starts a **create** watch for a NEW pod built by the same code as Recreate (`requestFromPod`: image, disk, cloud, idle stop, own configuration, hence the network volume, its datacenter, ports and environment) with the chosen card and `data_center_id` of the old pod: `pods.createLikeWhenFree(podId, gpu)`, MCP `create_pod {like_pod_id, gpu, retry_until_free}`. The new pod is named `<old name>-<card>`, never the old name: a create watch that lost an answer looks a pod up by name and would otherwise adopt the old pod. The watch row and the card say which card is awaited ("Waiting for a free RTX 4090 in EU-RO-1").
**Guard: the old pod is never deleted.** The like-request is only built, never acted on; the create watch calls `create` and nothing else (`podwatch.ts` has no terminate, stop or delete call), the popup says "Creates a new pod; this pod is not deleted.", and deleting stays a separate action on the card with its own confirm (Binc: nothing deleted without an explicit yes). Tested: core (`pods.test.ts`, no terminate or stop query), browser (`retry-later-modal.spec.js`, no DELETE call).

## Consequences

- One tag no longer means two images; Blackwell cards keep their CUDA 13 build.
- Anything a shell can do to bypass the gate stays possible until the guard is wired and shipped; it is a heuristic, not a proof.
- Until the weights and VAE choice are decided, nothing is downloaded and nothing is spent on this.

## Amendment (2026-11-17, section 19): a wait for a new pod belongs to the pod it was made from

Found when Lucas chose Retry Later > Another GPU on `CanalV2-base-graphs-v001-v27-a100` and saw no sign of the wait: the watch was saved (`pod-watches.json`), but a create watch carries the new pod's name, not the old pod's id, and the card showed only a resume watch for its own id.
- A create made through `createLikeWhenFree` now records `from_pod_id`; the card shows each waiting create made like it ("Waiting for a free RTX PRO 4000 in EU-RO-1: makes a new pod, this one is not deleted, trying every 2 min, next try 14:00, tried 4x") with its own Cancel. One saved before the field existed is matched by the name it carries (`<pod name>-<card>`).
- **One wait per pod:** a second create wait for the same pod is refused with a 409 that names the first (two cards would each make a pod when they freed); cancel the first to choose another GPU. A plain create with no source pod is not affected.
- **For agents (MCP):** `pod_retry_options { pod_id }` returns the popup's two options and the cards in the pod's datacenter plus the waits already on it; `pod_watch { pod_id }` lists the waits on that card (the rule is `podwatch.watchesFor`, shared with the window); `resume_pod` and `create_pod { like_pod_id, gpu, approved_by, retry_until_free }` start them, and `pod_watch { action: cancel }` stops one. The one-wait-per-pod guard and the never-delete rule apply to agents the same way.

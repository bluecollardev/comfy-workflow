# ADR-055: Delivery integrity and kept logs: the rules from 2026-11-20

**Date:** 2026-11-20
**Status:** Accepted. Built on `develop` (not yet released); the DPX header correction is built and unit-tested, and still has to be checked on real frames (section 3).
**Context from:** the Tunnel V11 delivery (the 20 Nov PDF, `docs/CANALV2-TUNNEL-V11-PRODUCTION-PLAN.md` section 9). Lucas: "deliver what we can", "test in `_TEST_` first before sending to the real path", "don't overwrite any existing stuff in the real `returns/BKK/` in any non-test directory", "we cannot have these defects", "don't delete the logs when done for the pods", "if you delete a pod, you lose the history, but in the event that it is stopped you do not". Builds on ADR-050 (publishing), ADR-052 (destructive actions) and ADR-038 (the queue).

## 1. A delivery round is never overwritten (built)
- In a round whose name does not start with `_TEST_`, a file that is already in the destination **with another size is refused**: the plan lists it under `refused`, the plan is not ok and `run` throws before anything is sent. A file with the same size is skipped, as before. Only a `_TEST_` round may be written over again. (`publish.ts`, after the listing of the destination.)
- A `RETURN-MANIFEST.json` that is already in a round and is not ours (not the app's schema, or another round's) is left untouched: the run fails with the 409 it already had, after the files are up, and nothing is overwritten. A manifest of the app's own schema is still merged, shot by shot, as ADR-050 says.
- The per-element manifest (section 2) is **written on every publish of the element** (Lucas, 2026-11-21: "manifest should be generated on publish"; before, one already in a real round was left alone, so 11 elements went out on 2026-11-21 without theirs). One already in a real round is replaced when it is ours (it carries our `schema_version`) or when the run has `allow_overwrite`; a manifest that is not ours is left as it is.
- **Test rounds also relax the EDL holds** (an existing behaviour). A delivery therefore goes to a `_TEST_` round first with the same layout and names, is checked in the bucket, and only then goes to the real round.
- **Why:** a re-published shot with a different file would silently replace what the client already has. The old behaviour was right for a scratch round and wrong for a delivery.
- **Amendment 2026-11-21 (Lucas: "delete your stupid safety shit", "i said publish"):** a run may now pass `allow_overwrite: true` (plan and run; the MCP `publish` tool takes it) to write over a file already in a non-`_TEST_` round with another size. It is **off by default** and the refusal stays the rule; a run still needs `approved_by` and `confirm`, and the request, with the flag, is kept in the job record. First used on 2026-11-21 for 11 elements whose round already held 8 to 29 sample frames each (384 bytes different from the corrected frames): the samples were replaced by the full corrected sequences.

## 2. A manifest per element (built)
The PDF's contents show `<CLIP>_MANIFEST.json` next to each element (6.6 to 83 KB, so it lists the files). Each element now gets `<shot>/<CLIP>_MANIFEST.json`: the round, who returned it, when, the pod, and the element's item with the sha256 and size of every file. They go up before the round's `RETURN-MANIFEST.json`, which stays last. Still to settle with Binc: whether the round-level manifest is wanted besides.

## 3. Corrected copies of the DPX (built; checked against the spec, not yet against a viewer)
The frames the pipeline writes tag the picture as linear (transfer and colorimetric 2) while the pixels are Gamma 2.6 P3-D65, and carry no timecode. The PDF calls the linear tag a bug and ships a corrected copy for CGI-072 with "colour code user-defined instead of linear; pixels unchanged". `libs/core/src/dpxfix.ts` (MCP `dpx_fix`, named yes) writes **copies** under `comfy-shared/output/_delivery_v11/<clip>/<clip>.NNNN.dpx` on a pod that has the volume; the originals are never touched. Per frame, in the 2048-byte header only: transfer and colorimetric 0 (user-defined); the TV header's time code (BCD HHMMSSFF, the clip's start timecode plus the frame index) and temporal sampling rate (the frame rate) and gamma (2.6); the film header's frame position, sequence length and frame rate; the image file name. The picture bytes are copied unchanged, the size is checked and every header is read back. Both byte orders are handled.
- **In the window and in MCP.** Outputs > **Prepare For Delivery** lists the DPX sequences with the clip name and start timecode the EDL gives each (one not in the EDL is not offered), the frame rate (24 for the `_24_` photoreal clips), asks for a name, writes the copies on the running pod and shows each one as written and checked; then it opens Publish. MCP `dpx_fix` has the same two steps: `plan` (read-only: the clip, timecode, fps and whether the EDL holds each back) and `run` (named yes, a running pod).
- **Open:** "user-defined" is what the PDF says for the CGI-072 fix; if Binc's corrected files carry another code, match them. The offsets follow SMPTE 268M; compare a corrected frame with one of Binc's before the real round.
- **The H.264 proxy's timecode** is a separate matter (the PDF's second defect for CGI-072); the review videos carry the timecode their render gave them.
- **Disk:** a corrected copy of a sequence doubles its space on the volume (91 GB for the 17 elements; the volume has 2,500 GB).

## 4. Pod logs are kept (built)
A pod's logs are lost when the pod is deleted; they stay while it is stopped. `podlogs.ts` writes them to `pod-logs/<day>/<pod name>_<pod id>_<time>.log` in the config folder, never over an older file: at the end of each run task, just before a pod is stopped, just before it is deleted (by anyone), and on demand (MCP `pod_logs`: save, list, read; the pod's logs window has the list, the viewer, Save Logs Now). Each file holds the RunPod container and system log and ComfyUI's server log. **Nothing deletes a log by itself.** A person deletes them: "Delete This Pod's Logs" or "Purge All Saved Logs" (after a yes), or MCP `purge` with `confirmed: true` after asking. The test suite switches the saving off (`POD_LOGS_OFF=1`).
- **Pods are stopped, not deleted** (Lucas, 2026-11-20: "let them stop", "I want to see what is there"). The five import pods that were deleted that day lost their RunPod history; what they produced is on the volume.

## 5. A job that failed can be retried, and says so (built, v1.7.0)
A publish run keeps the request it was asked to do with its record; a render job the same. A failed shot of a run from before a restart is sent again as a new job from that request (the files already in the bucket with the same size are skipped); a failed or cancelled render job starts its unfinished sequences again. The status carries `retryable`, never the request. A job from before this was kept shows **Retry** disabled, with the reason, not hidden. Each Retry shows a spinner and a toast.

## 7. The application's own log is collected (built, Lucas 2026-11-20: "make sure we collect any logging from the application")
Before, the app kept only `stalls.log` (what froze the window), `history.jsonl`, `failures.jsonl` and the sync logs; what the main process printed (`console.error` of the idle watch, the MCP host, a crash) went to a terminal nobody reads. `electron/app-log.cjs` writes `app-logs/<YYYY-MM-DD>.log` in the config folder, one line each (`time LEVEL text`): every console line of the main process (still printed too), unhandled exceptions and rejections, the page's warnings and errors (`console-message`), a page that failed to load or whose renderer is gone or not responding, a child process that died. Secrets are cut out before a line is written (keys, bearer tokens, a signed link's signature, a Slack webhook), a line is cut at 4,000 characters, a day stops at 50 MB. `libs/core/src/applogs.ts` and the MCP tool `app_logs` list the days, read one (by level, by text, the last N lines) and purge (a person's yes, `confirmed: true`). Nothing deletes an app log by itself. The test suite for it is `electron/app-log.test.cjs` and `libs/core/tests/applogs.test.ts`.

## 8. A master video is unpacked into DPX, straight (built, not yet run on a pod; Tunnel V11 plan section 12 step 2)
For the 16 elements that exist only as a finished video, `libs/core/src/dpxmake.ts` (MCP `dpx_make`, `plan` and `run`) writes the 16-bit DPX sequence on a pod over SSH, the way `dpxfix` does. The master is a path under the volume's `comfy-shared/` (`temp/rounds/<round>/<shot>/approved/05-outputs/Approved/master/<file>.mov`, also .mp4 or .mxf); the frames go to `output/<round>/<shot>/<shot>_<element>/dpx/<shot>_<element>_<round>_NOT_RELEASED.NNNN.dpx`, from 0000, round `mono_v019` unless told. Decisions:
- **Straight.** One filter, `scale=in_range=<tv|pc>:out_range=pc:in_color_matrix=<m>,format=rgb48le`: the range the master is tagged with (tv when untagged) is expanded to full and the YCbCr to RGB matrix is applied (the master's tag: bt709, bt601 for smpte170m or bt470bg, bt2020 for bt2020nc; bt709 when it carries none, and then the result says `colour.tagged: false` and a note). No primaries or gamma are converted: the DPX header is not told anything either (step 1 of the plan decides that).
- **Never over anything.** The script refuses (that item fails, nothing is written) when the dpx folder already holds files. It writes into a hidden temporary sibling folder and renames it into place (`mv -T`) only when the frame count equals `frames_expected` (when given) and the first frame's header says 16-bit (byte 803); a failed item removes only its own temporary folder.
- **Named yes, one item at a time.** `approved_by` is required, every name is validated (plain characters, no `..`, no leading slash, nothing the shell could read) before a pod is asked, every value is quoted into the script, the run is one entry in History, a failure stops that item only. `plan` is read-only and asks no pod.
- **An element is a cut of its master, not the whole master** (Lucas, 2026-11-21). `source_ranges: [{ in, out }]` (HH:MM:SS:FF; `in` inclusive, `out` exclusive, as in the CMX3600 EDL, whose source-out is the frame after the last one used; ascending, no overlap, at most 20) unpacks only those frames, in order, into ONE sequence numbered from 0000. The pod turns each timecode into a master frame number at the master's own rate (base round(fps), non-drop: 23.976 counts 24), minus the master's start (`start_timecode_of_master`, else the master's own `timecode` tag, else 00:00:00:00; a NOTE says which), and selects them with `select='between(n\,A\,B-1)+...'` before the scale filter, with `-fps_mode passthrough` (`-vsync 0` when the pod's ffmpeg has no `fps_mode`) so no frame is duplicated or dropped. The count must equal the sum of the ranges and `frames_expected`, or nothing is put in place. `plan` returns the master frames each range maps to. `from_edl: true` (with `shot`, `element`) takes `frames_expected`, `source_ranges` and `fps` from the loaded EDL (load it first; a retimed element is refused). Absent `source_ranges` = the whole master.
- **Tested** with the real ffmpeg when it is installed: a ProRes 422 HQ clip tagged bt709 tv is unpacked by the same arguments the module builds; five files numbered 0000 to 0004, 16-bit, and a mid-grey source comes out at mid-grey full range. Not yet run on a pod and not yet in the Outputs window.

## 10. The element manifest has an `issues` section (2026-11-21, `feature/manifest-issues`)
Lucas: the manifest was going to have an issues section. None was designed before, so this is the smallest one. Each `<CLIP>_MANIFEST.json` carries `issues: [{ code, severity: warning|info, text }]` next to `item`, written on every publish with the rest of the file (so a republish re-derives it).
- **Derived, never guessed**, from what is in the element's outputs by `issuesOf` (`publishlayout.ts`): `no-dpx` (proxy only), `no-frames` (DPX count zero), `no-review-video` (neither ProRes nor H.264; a warning when DPX exist), `no-h264` (ProRes only, info). An empty list means none of these was found, not that a person checked the element.
- **More codes, from facts publish holds or reads (2026-11-21, `feature/manifest-issues-2`)**, `issuesOf(item, facts)`: `frame-count-mismatch` (warning; the delivered DPX count against the EDL cut of the element, both numbers in the text; only when the EDL is loaded and matches), `colour-unstated` (info; a review video exists and its `.meta.json` records neither `colour_in` nor a colour source), `header-disagrees-record` (warning; the review's `.meta.json` says `header_disagrees`: the DPX header and the OCIO record differ, the record was used), `review-colour-differs` (warning; the review's `colour_in` is not the `current_colour_in` passed in; the publish request has no colour statement today, so this stays silent until a caller passes one), `review-fps-differs` (warning; the review's rate in its `.meta.json` against the rate in the delivered name, the symptom of the 24 fps first pass), `stray-files` (warning; DPX in the element's own frame folder on the bucket that are not its frames, with their sizes: the 49,768,448 against 49,768,064 case; from one read-only recursive listing of the round, left out when it cannot be read).
- **Not raised, because the facts are not recorded:** "the review was made from pre-patch frames" (no `.meta.json` field says so; `review-fps-differs` is the observable part), and "the colour statement is unsettled" between people (a decision, not a file fact).
- **Failed generations are round level, in `ISSUES.json`**, written next to `RETURN-MANIFEST.json`: an element with no frames has no manifest of its own. Each entry is `{ shot, element, code: 'not-generated', severity, text, failure }` where `failure` has the `failures` tool's fields (stage, node, message, recovery, retryable, attempts, at, pod, job_id) of the latest record for that element, or `null` when none is on record. The element is read from the failed graph's path (`base_v008/photoreal-013/photoreal-013__f23__base_v008.json` is photoreal-013 and F23; the failures log mostly has no shot of its own), kept only if the loaded EDL knows it, and only for shots that are in the round's manifest. The record shown is the latest one: for a graph killed for memory it is often the 502 on `/history` with the transient-error recovery text, because the app only knows the OOM when RunPod's system log says so. It is a sibling file, not a field in `RETURN-MANIFEST.json`, because `mergeManifest` refuses (409) a manifest whose `schema_version` it does not recognise and Binc's readers may be strict about `bh-return-1`; the file carries `schema: 'bh-issues-1'`, is replaced when it is ours and left alone when it is not, and is not written when there is nothing to say. A failure to build it never fails a publish.
- **`RETURN-MANIFEST.json` is unchanged:** its items are the `bh-return-1` schema (Binc's), so the section is only in the per-element file. Elements already delivered get it when they are next published.

## 11. Frame previews are a pod job (built 2026-11-21, Lucas: "that's why these are jobs"; branch `fix/outputs-load-frame-previews`)
A DPX frame is 8 to 50 MB, so this PC never pulls frames to make a thumbnail. **Frame Previews** is a JOB that runs where the files are: `libs/core/src/framepreviews.ts` runs a small python script (numpy and Pillow, both ComfyUI's own requirements) on a running pod that has the volume, over SSH (the way `dpxfix` and `dpxmake` run), and writes one JPEG per frame (320 px wide, quality 80, about 30 KB) under `output/.previews/<the sequence's folder under output/>/<frame name>.jpg`: a mirror tree beside the deliveries, never inside a delivery folder, so a publish never picks one up.
- **Idempotent:** a frame that already has a non-empty JPEG is skipped; a JPEG is written as `.part` and renamed; nothing is deleted. With Skip Existing unticked every JPEG is made again (the new one replaces the old, atomically).
- **A preview only, never colour truth:** the code values get a plain display tone (`gamma26`: Gamma 2.6 display to a Gamma 2.2 screen, the default; `linear`: the sRGB curve; `none`), because the headers of this project's frames say linear over Gamma 2.6 pixels. Decoder: 16-bit and 8-bit RGB and 10-bit filled (methods A and B) DPX; anything else is a failed frame with its reason, the batch goes on.
- **A job like the others:** two worker threads on the pod (a CPU job), progress lines, Stop (ends the ssh session; the script stops at its next progress line), one entry in the shared running-jobs file (kind `volume`, label `frame previews ...`) so the app and MCP both see it and either can cancel it, a History line at the end. MCP tool `frame_previews` (start, status, cancel, list); IPC `framepreviews`.
- **In the window:** an expanded sequence has `Load Frame Previews` (and `Stop`) in its header, `N of M frames show previews` (counted from the pod's one listing plus the first-frame cache), the JPEGs on the rows through the same /view address as any file, a warning mark on a frame the pod could not decode. The Generate window's Previews panel has a mode choice, `Sequence Previews` (today's first-frame thumbnails, unchanged) and `Frame Previews` (this job over every in-scope sequence; counts are frames: `1,820 ready · 4,100 waiting · 0 failed frames`); Skip Existing applies to both; the mode is remembered for the window session. With no running pod the button is disabled with the reason.
- **Cost:** the job reads each frame once on the pod (local disk, no network). Per frame (estimate, not measured on a pod): about 0.3 s for 1920x1080 (8 MB) and 1 to 2 s for 3840x2160 (50 MB) per worker, so 94 frames at two workers take about 15 s (HD) to 1.5 minutes (4K). What crosses the network is the JPEGs, about 30 KB each, when a row is shown.
- **Not built:** saved pod logs for this job (the script's lines are in the job record and the History line only); an automatic start (only a click starts it); previews for single files that are not DPX sequences.

- **Relaunch (built 2026-11-21, Lucas: "have a way to relaunch this"; branch `feature/frame-previews-relaunch`; live after the next restart).** A job that failed or was cancelled (tonight: `the script ended with code 255` because its pod had been stopped) is run again by `relaunch(job_id)`, MCP `frame_previews` action `relaunch`, and the window's `Relaunch` button (Generate window, Frame Previews). The job record keeps `done_dirs` (folders the script finished without an error); a relaunch runs the SAME folders minus those, with the same tone and `skip_existing` always true, so a frame that has a JPEG is never made again, and the new job names the old one in `relaunch_of`. **Pod:** the explicit `pod_id` if it runs, else the old job's pod if it runs, else the first running pod that has the same network volume, never one in `exclude_pod_ids`. **It never resumes or creates a pod** (that spends; it stays a person's act): with none running it answers `needs_pod` with the stopped pods, and the window shows `No pod is running: Resume A Pod first` with a `Resume Pod` button per stopped pod, which asks first and then uses the normal resume. A job still running answers 409; a job the app no longer knows (job records live until the app restarts) answers 404; when every folder had finished it answers `nothing_to_do`. Finished, failed or cancelled jobs also get `Remove` in the window (clears the window's record; the JPEGs stay). In the Queue's Pending Uploads a dry-run entry's `Cancel` reads `Remove` (waiting entries keep `Cancel`).

## 12. Prepare For Delivery's settings are a configuration block (built 2026-11-21, Lucas: "use the settings in Prepare For Delivery as truth to run" and "make sure those settings are export / importable via our configuration import export"; branch `feature/delivery-prepare-config`)
What `dpx_fix` writes used to be fixed in the code (the folder `_delivery_v11`, colour code user-defined, gamma 2.6, the frame rate from the clip name, the film header set). It is now the block `delivery_prepare` of the **Default Configuration** (`libs/core/src/mounts.ts`, `DeliveryPrepareConfig`), next to `auto_publish`, `outputs` and `edl`:
- **Fields and defaults** (an older configuration without the block loads with exactly these, no error): `out_dir` `_delivery_v11` (one plain folder name under the volume's `output/`), `colour_code` `user-defined` (`linear` writes code 2, what the pipeline wrote), `gamma` 2.6 (0.1 to 10), `fps_source` `clip-name` (24 for a `_24_` clip, else `fps`; or `fixed`: always `fps`), `fps` 23.976 (1 to 120), `timecode_source` `edl` (or `zero`: 00:00:00:00 for every clip), `frame_position` `set` (frame position, sequence length and frame rate in the film header; or `keep`: left as written), `skip_existing` `false` (a copy already there with the right size is kept; the read-back check still runs on it). Originals are never touched, whatever the settings.
- **What is NOT in it:** `approved_by`. A person's yes is not a setting: it stays in the window (browser storage) and in each call, is recorded in History, and an imported file that carries one is refused (as Auto-publish's standing approval is never imported, ADR-050). The EDL is not copied into it: where the EDL is read from is already the `edl` block, which travels in the same section; the clip name and the start timecode still come from it.
- **Who reads it:** `dpxfix.settings()` is the stored block; `dpxfix.effective(item)` puts a call's own arguments on top (an item may carry `out_dir`, `colour_code`, `gamma`, `frame_position`, `skip_existing`, `fps`, and may leave out `start_timecode` when `timecode_source` is `zero`) and validates the result like a saved block, so a bad argument is a 400. `plan` returns `settings` with its rows and the rows already follow `fps_source` and `timecode_source`; `run` returns the settings it used. The Prepare For Delivery window reads the same block (its intro and a "Settings in force" line say what will be written, the rates and timecodes in its table follow it), and the MCP tool `dpx_fix` says so. A plan flag (not in the EDL, frame count differs) still blocks, whatever the settings.
- **Where it is edited:** Default Configuration window, a box "Prepare For Delivery" (not in a pod's own configuration: `podconfigs` strips it like `auto_publish`). `get_configuration`, `set_configuration` and `preview_configuration` carry it (a patch merges field by field).
- **Export, import, backup, undo:** the block is in the Pod defaults section of the export (`configio.SECTIONS.pod_defaults.fields`, `CONFIG_KEYS`, a type check that also refuses `approved_by`); import plan and apply merge it onto the current configuration like the other blocks; the backup holds the whole configuration, so Undo puts it back, and a backup written before the block existed restores to the defaults. Every writer that saves the whole configuration spreads `mounts.load()` and keeps it: `put`, `save`, `mcp.setServe`, `volumes`, `wantedmodels`, `autopublish.writeStored`, the MCP `set_configuration` merge. **The known trap stays:** `mounts.put` of an object that leaves the block out resets it to the defaults, like every block; use the setters or put the full loaded configuration. A test covers each path (`libs/core/tests/delivery-prepare-config.test.ts`).
- **Not built:** per-pod overrides of these settings (a call's own arguments cover a one-off); a History line for a change of the block beyond the generic "saved Default Configuration".

## 13. Auto-publish uploads the corrected copies of the DPX (built 2026-11-21, Lucas: "dpx_fix is wired in. fix #12"; branch `feature/dpx-fix-in-pipeline`)
**What was wrong.** With `include_dpx` on, Auto-publish uploaded the ORIGINAL frames the review's sidecar names (`delivery_v008/<clip>/`): the wrong header (linear flag, no timecode), the defect `dpx_fix` exists to remove. Nothing in `autopublish.ts`, `publish.ts`, `queue.ts` or `runflows.ts` called `dpxfix.ts`.
**What it does now** (`libs/core/src/dpxprep.ts`, used by `autopublish.ts`): before a review's DPX go into an upload plan, `dpxprep.prepare` does what Prepare For Delivery does. It asks `dpxfix.plan` for each sequence the sidecar names (clip name, start timecode and frame rate from the EDL, taken verbatim), then runs `dpxfix.run` with the Default Configuration's `delivery_prepare` settings and the standing approver as the named yes (`skip_existing: true`, so a copy that is already complete is read back, not written again), on the best running pod of the volume (`publish.rankedPodsOnVolume`: an idle pod before one that is rendering). The upload plan then carries the corrected folder `output/<out_dir>/<clip>/` (default `_delivery_v11`), never the original frames.
- **Held, nothing uploaded** (not even the video; the reason is in the Skipped list as `held back: dpx fix: ...`): the plan carries a flag (held back by the EDL check, no start timecode), the frame count differs from the EDL cut (a `_TEST_` round waives only this, with a note), there is no approver or no running pod, or the fix fails or does not read back all its frames. A fix that failed at upload is not tried again for ten minutes.
- **Video only, with the reason:** the sequence is not in the EDL, or its frames are not on the volume.
- **Dry run writes nothing:** the plan runs (so the flags show) and the corrected copy is listed only when it is already there; otherwise the note says it is made at upload.
**Setting.** `auto_publish.fix_dpx` (default true, part of the Default Configuration, carried by export and import, validated as a boolean; an older file without it loads with it on). `include_dpx` on and `fix_dpx` off means the DPX are never uploaded (the review video only), and the status says so (`status().dpx`: `include`, `fix`, `mode`, `fixing`). The Auto-publish settings window has the checkbox `Fix DPX Before Upload`. `include_dpx` off behaves as before.
**Not done.** The fix is wired into Auto-publish only: Import Round and the queue's run tasks still leave `dpx_fix` to Prepare For Delivery (or the MCP tool); a render finished by hand is not fixed until a person runs it. The old check of the original frames (`edlCheck`) is gone. `dpxfix.run` is never run in a test against a real pod.


## 14. Manifest repairs are code, not hand edits (built 2026-11-21, Lucas: "make sure the manifest generation is done programmatically"; branch `feature/manifest-check-rebuild`)
**What was wrong.** Publish already writes the element manifests, `RETURN-MANIFEST.json` and `ISSUES.json` by code, but on 21 November three stale bundled `main` items had to be removed from `RETURN-MANIFEST.json` with a one-off script (the original kept as `RETURN-MANIFEST.backup-before-fix.json`). A manifest that is wrong should be repaired by a tool that checks first, keeps the old file and verifies the new one.
**`manifest_check`** (`libs/core/src/manifestcheck.ts`, MCP tool, IPC `manifestcheck.check`): read-only, over the app's Panama S3 access. For a round it reads every `<CLIP>_MANIFEST.json`, `RETURN-MANIFEST.json` and `ISSUES.json` and reports per element: files in the manifest against objects in the bucket (names, sizes), files in the frame folder the manifest does not list, frame count against the manifest's own file list and the EDL cut, a missing sha256, a missing `issues` section; for the round: DPX folders with no element manifest, `RETURN-MANIFEST` items with no element manifest (stale), bundled items (an item that is not an element), duplicates, items that differ from their element manifest; and a summary count.
**`manifest_rebuild`** (MCP tool, IPC `manifestcheck.plan` / `.run`): `plan` shows the diff (items before and after, added, removed, changed, the `ISSUES.json` change, the backup name, blockers) and writes nothing. `run` needs `approved_by` and `understood: true`, refuses while a publish job targets the round, takes the round's write lock, and refuses when an element manifest is unreadable or lists a file that is not in the bucket. It first writes the previous manifest to `RETURN-MANIFEST.backup-<UTC stamp>.json` in the same round folder (read back; never deleted), then writes exactly one item per element manifest in the `bh-return-1` shape and field order (`returned_by` and `pod` kept, `returned_at` now), reads it back and compares. `ISSUES.json` is regenerated with `roundIssuesOf` from the same facts as a publish (ours only; one that is not `bh-issues-1` is left alone). With nothing to change, a run writes nothing and makes no backup. A missing element manifest is reported, never guessed.
**Not done.** No button in the window (IPC only); the tools ran against fakes only, not the real round; Auto-publish jobs are not checked for the round, only publish jobs; the backup of `ISSUES.json` is not kept.

## 15. The pod Outputs window loads faster: pool and cache, thumbnails, video posters, Generation Errors (built 2026-11-21, Lucas: "the generated previews take a long time to load, can we have thumbnails too?", "first frame as a poster", "keep this change small"; branch `feature/preview-thumbnails`)
**What was slow (read from the code and measured with the browser fakes).** A strip or grid asks `/view` for one JPEG per frame, and every request went through the `podfile://` handler: one fetch to RunPod's proxy each, no limit, no memory (the handler forwarded no caching header), so every open of the window downloaded them all again. The sequence tile's own image read a whole 50 MB DPX and decoded it in the page, one at a time, after a click, even when the pod already held a 30 KB JPEG of that frame. Each video tile opened a `<video preload=metadata>` per visible tile (a few player slots), which reads the file's header from the pod.
**What changed.**
- **Pool and cache (`electron/previewcache.cjs`, used by the `podfile://` handler for `/view` addresses under `.previews/` only):** at most 8 fetches at once, one fetch per address however many tiles ask, a memory cache of 1,500 small image answers kept 30 minutes, and `cache-control: private, max-age=3600` on the answer. Only HTTP 200 images under 2 MB are kept. A delivery, a render or a video is never touched by it.
- **Thumbnail tier:** the frame-previews script also writes a 160 px, few-KB JPEG per frame under `.previews/<folder>/thumbs/<frame>.jpg`, made from the 320 px JPEG when it exists (the DPX is not read again) and never failing a frame. A re-run with Skip Existing ticked adds the missing thumbnails to previews made before this change, so Load Frame Previews doubles as "make thumbnails". The strip and the frame grid (112 px tiles) load the thumbnail when `list` says it exists and fall back to the 320 px JPEG when it does not. `list` (with names) now also returns `thumbs` and `posters`.
- **First frame at once:** a sequence tile shows the pod's 320 px JPEG of its first frame straight away (`outputs-dpx-quick`) instead of a "Load preview" click that read a 50 MB frame; the decoded preview still replaces it when loaded (it brings the colour chips).
- **Video posters:** the same job takes items of `kind: 'posters'` (a folder of videos) and writes each video's first frame with ffmpeg, 320 px, to `.previews/<folder>/posters/<video name>.jpg` (additive, Skip Existing, a broken video is a FAIL line). A video tile shows its poster, or a film icon when none exists, and creates **no `<video>` until play is clicked** (`preload="none"`); the old behaviour of a player per visible tile is gone. Load Frame Previews sends the folders of the videos in scope as poster items.
- **Generation Errors (N):** a collapsed section in the Outputs window, absent when nothing failed, listing this pod's Frame Previews job error and failed frames, the preview batch's failed sequences and the graph failures log (by pod), each with what, why and when, and `Relaunch` for a failed Frame Previews job. It reads the records the app already keeps.
**Dropped as follow-ups (Lucas: keep it small):** a disk cache for previews; a `Make Thumbnails` button and MCP action (Load Frame Previews with Skip Existing does it); contact sheets; the other views that show videos or sequences (the Queue's review rows, Pending Uploads, the Outputs window outside this modal) do not use posters or thumbnails yet; `s3file://` (a volume with no pod) addresses are not pooled or cached; Load Frame Previews is disabled when only posters are missing.

## 16. Failures can be dismissed from the Queue (built 2026-11-21, Lucas: "Failures (50) in queue have ability to dismiss"; branch `feature/dismiss-failures`)
`failures.jsonl` (the graph failures log) stays the audit record: nothing here edits, rewrites or deletes it. A failure is dismissed **by id**: the id goes into `failures-dismissed.json` next to the log (rewritten whole through a temp file, one change at a time, capped at 5,000 ids, a damaged file hides nothing), so the dismissal survives a restart and **a new failure always shows**, even after Dismiss All. The Queue's list (`failures.list` default `dismissed: 'hide'`) and its `Failures (N)` count, the Overview alert and the header all count only what is shown; `dismissed: 'only'|'all'` and `dismissed_count` give the rest.
**Window (Queue > Generations):** `Dismiss` on each row, `Dismiss All` (a confirm names the count and says nothing is deleted: the records stay in the failures log file and in the History, and a new failure still shows), `Show Dismissed (N)` opens a list of the dismissed ones with `Restore` each and `Restore All`. The Queue's CSV/PDF export still includes the dismissed ones. Each dismiss or restore writes one History line (`failures dismissed`, `failures restored`).
**Core and tool:** `failures.plan` (how many a dismiss or restore covers, nothing written), `failures.dismiss`, `failures.restore` take `{ ids }` or `{ all: true }`. The MCP `failures` tool has `action: list | dismiss | restore`; dismiss and restore are plan-then-run like the other app-state writes: without `understood: true` the answer is a plan (`{ plan: true, count }`), a run needs `approved_by` (a person's name, never invented) and `understood: true`.
**Not done:** the Generation Errors section of a pod's Outputs window lists the graph failures that are not dismissed (it asks for the default view) and has no Dismiss of its own; the dismissed set is not exported with the configuration; failures older than the log's 4 MB read window are not counted in `dismissed_count`.

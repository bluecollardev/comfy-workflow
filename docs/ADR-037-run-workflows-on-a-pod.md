# ADR-037: Run workflows on a pod, from the pod card and from MCP

**Date:** 2026-11-07
**Status:** Accepted; built on `feature/run-workflows` (unit and browser tests pass). **Not yet run against a real pod**, and the pod-side converter needs a new image tag (not built or pushed; a push needs a named yes).
**Extends:** ADR-028 (MCP can do everything the window can), ADR-033 (a round's graphs are placed in the Workflows panel), ADR-036 (the image bakes in no workflows). Uses the History (`libs/core/src/history.ts`).

## Context

Lucas (2026-11-07): "have a button on pod cards called run workflows. running this should log any errors to our logs", then "run workflows should run all workflows in shot", then "it should pop open a modal that allows you to select which workflows to run for the pod", and "this should also be exposed to mcp".

A pod's Workflows panel holds **UI graphs** (nodes with positions and links; settings stored by position). ComfyUI's `/prompt` queues only **API graphs** (node id -> class and named inputs). The UI's Run button converts in the browser; the bridge's `queue_prompt` refuses a UI graph. BH's round graphs are UI graphs only (the cgi-042 delivery graph: 89 nodes, no API twin), so running them needs a conversion.

## Decision

1. **A "Run workflows" button on a running pod's card** opens a modal. It lists the graphs in the pod's `comfy-shared/workflows`, grouped by folder (a shot or a round; inputs manifests and API twins are not listed), **all ticked**, with Select all / none and a tick per folder. Run starts the ticked graphs, one after another, on that pod, and shows each graph's state (waiting, running, done, failed, skipped) with its error.
2. **The conversion is ComfyUI's own frontend**: load the graph, `app.graphToPrompt()`. That is the Run button's code, so muted and bypassed nodes, reroutes and primitives behave as in the UI. Two ways to reach a frontend, tried in this order:
   - **On the pod** (`apps/comfy-app/docker/ui2api.py`, run over SSH): a headless Chromium on the pod opens `127.0.0.1:8188`. Needs the image to carry Chromium and Playwright (about 300 MB, `Dockerfile`); present only in images built after this ADR.
   - **On this PC** (`libs/core/src/ui2api.ts`): Chrome headless through `playwright-core` opens the pod's own page over its proxy. Works with today's pods; needs Chrome on this PC and the app (or MCP server) running here.
   The pod way is tried first; an image without the script falls back to this PC. A graph that the pod's frontend failed to convert is a failure, not a reason to retry elsewhere.
3. **Every outcome is logged to the History**, one `job` event per graph with `job: "run"`: `done`, `failed` (with the error text) or `cancelled`, the graph path, the pod, the prompt id, the seconds, and the node where it failed. Errors are the ones ComfyUI gives: a rejected prompt's first invalid node (and how many more), an `execution_error` (message, node id, node type), a conversion failure, a graph that is not a UI graph, a locked shot, a timeout. A failed graph does not stop the rest.
4. **Locked shots are refused**, the same rule as `queue_prompt` (`shots.lockedIn`): client-approved shots are never run by us.
5. **MCP has the same actions** (ADR-028): `list_pod_workflows {pod_id}`, `run_pod_workflows {pod_id, paths, approved_by}` (returns a job) and `run_workflows_job {id, cancel?}`. Running needs `approved_by` because it uses GPU time on a pod that is already billing; the window's button does not ask (the user is there and pressed it), as with Pull.
6. **Cancel** stops the job: graphs not yet started are skipped and the running prompt is interrupted (`POST /interrupt`).

## Not decided

- **Inputs that change per run** (a different frame range, a different plate): a graph is run as placed. Editing values before a run is for the Workflows panel.
- **Order and parallelism**: graphs run in the order ticked, one at a time (a pod has one queue; stacking prompts would hide which one failed).
- **Where the picked "shot" comes from**: the modal groups by the panel's folders. ADR-033 places a round's graphs under `workflows/rounds/<round>/`; a per-shot folder inside is used if the round has one.

## Consequences

- A user (or an agent) runs a round's graphs on a pod without opening ComfyUI's page and sees every failure in the History, with the same filters as pulls and syncs (`run`).
- The packaged app gains a dependency, `playwright-core` (no bundled browser).
- Until a new image tag is built and used, conversion happens on this PC.
- Untested against a real pod: the page-side calls (`window.app.loadGraphData`, `graphToPrompt`) are those of the current ComfyUI frontend and could change with it. The first live run goes in the runbook's Log.

## Amendment (2026-11-15): two steps, Outputs

- Run Workflows has two steps, **Run** and **Outputs** (the shared `StepperNav`). Pod cards show Import · Run · Outputs; Outputs is off until the pod has any.
- Each prompt is tagged `extra_data.pod_manager.workflow`, so outputs are listed by the workflow that made them (read from ComfyUI's history), filtered by the pod's shot.
- The viewer is an overlay (Esc and arrows); files download singly or **as one zip** (streamed, stored). Previews go through a `podfile://` protocol served by the main process, because RunPod's proxy refuses cross-site page requests.

## Amendment (2026-11-17): the window keeps its state; a split pane with reports and logs

**Context from:** Lucas ("when i close modal i lose state"; "i want a split plane larger modal left has the folder list right has reports / logs"; "our rounds import has better reporting and logging back to user"; "make this stateful first so i don't lose my run selection / progress").

1. **State (built 2026-11-17, uncommitted on `feature/volumes-v2-fallback`).** The run lives in the core, not in the window: `runflows.latest(podId)` returns a pod's current run (the one still running, else the newest). Reopening the window asks for it, shows each graph's state, picks up polling if it is still running, and re-ticks the run's graphs. What was ticked is kept per pod in `localStorage` (`stores/runflows.js`), so it survives closing the window and restarting the app; a window opened from a round still starts from that round. MCP: `run_workflows_job` takes `pod_id` for the same lookup (parity: `runflows.latest`). Tests: core (`latest`), browser (close and reopen keeps ticks and finds a running run), MCP parity.
1a. **The card's Run button shows a run in progress (built 2026-11-17).** Lucas: "on cards, if a run is in progress, show that in the same Run button"; the label is **Running** (with a spinner); "i should be able to open and see progress". While the pod runs, the card asks the core for the pod's latest run every 2.5 s (in memory, no network); a run in progress turns the same button blue, labelled Running, with "{done} of {total} workflows finished" as its tooltip. It stays clickable and opens the window on that run (point 1), with Cancel and each graph's state; when the run is over the button says Run again. Browser test: `run-workflows.spec.js`, "while a run is in progress the Run button says Running".
2. **Split pane (written 2026-11-17, not yet tested or built; Lucas said to hold tests until he says build).** The window becomes large (`xl`): the folder list on the left (groups, ticks, a badge per graph, a filter), a report on the right for the graph selected: state, seconds, prompt id, the failing node and error, the models used, the outputs gallery, and the ComfyUI log for that run (`comfyruns.logs`, cut to the run's start and end). A job header above both: graphs done of total, elapsed, an ETA from the average, a striped bar, as the import's job card shows (`VolumeJobView`, the Queue).
3. **A log of the run itself (written, same status).** `RunJob.log`: one line per step (run started, starting k of n, converting, pod models applied, queued as prompt, a heartbeat every 30 s, finished or failed with the node and error, cancelled, run finished; at most 500), plus `started_at` on each graph. Kept in the core and returned by `job` and `latest`, so the right pane and the MCP show the same thing. The window reads `job.log` defensively: with a core that predates it the pane still shows progress and the report, and the log says "No log yet" until the app is relaunched on the new core. The window is `xl`: the folder list on the left (click a row to select it; the selection follows the running graph until you do), and on the right a progress header (n of total, a bar, elapsed, the graph running now), the selected graph's report (state, time, prompt id, outputs, models, the failing node and error) and the log (this graph or all, scrolling to the newest).
4. **Surviving an app restart (planned).** Jobs are in memory: a restart loses the app's tracking, though the prompt keeps running on the pod. Persist the job to a file like the pod watches, mark a lost one **Interrupted**, and offer **Reattach** by reading the pod's ComfyUI history by prompt id, as the Queue does for a pull.
5. **Not changed:** Run still needs `approved_by`, refuses locked shots, and writes every result to the History.

## Amendment (2026-11-17): Outputs for writer nodes and the DPX quick-look viewer

1. **What the gallery receives.** The core lists the files a writer node such as `OCIOWrite` saves (a 16-bit RGB DPX sequence, e.g. 25 frames of about 3840x2160 and 50 MB each, plus a `.json` sidecar), so the Outputs gallery gets them as kind `other`. Browsers cannot decode DPX and ComfyUI's `/view?preview=` cannot either. The core's kind mapping is unchanged; the UI adds the kind `dpx` by file extension.
2. **One tile per sequence.** `galleryTiles` (`src/utils/outputs.js`) groups the `.dpx` files of one folder that differ only by frame number into ONE tile with a placeholder icon and a badge ("DPX · 25 frames"); nothing is fetched for a tile. A lone `.dpx` is a one-frame tile. Other files keep their tiles, and Download all (zip) still holds every file.
3. **The viewer** (`DpxViewerModal.vue`, decoder `src/utils/dpx.js`). It fetches one frame at a time from the same address the other viewer uses (`podfile://` in the app), decodes it in the page and draws it on a canvas, with a frame slider, Previous/Next, the arrow keys, the frame number, a loading line and an error line. Open and Download act on the current frame's file. It keeps the last 6 decoded frames, aborts a download it no longer needs and fetches the next frame in the background. Decoded: 8, 10 (filled, methods A and B), 12 and 16 bit; RGB, RGBA (alpha dropped) and luma; both byte orders; end-of-line padding. Downscaled by a whole box factor to at most 1920 wide. Not decoded: other descriptors (YCbCr, planar), 10/12-bit with packing 0, float.
4. **A preview, not a review.** The values are read as display-referred (the files are "Gamma 2.6 P3-D65 - Display", clipped) and mapped linearly to 8 bits: no colour management. Use DJV for real review. Checked on a real 3840x2160 frame from a pod (little-endian, 16-bit, packing 0, descriptor 50, data offset 1664): a clean picture, no skew.
5. **Playback.** The viewer plays a sequence like a video through the shared transport bar (`TransportBar.vue`): Play/Pause (Space), a scrubber, frame step, an fps selector (12, 24, 25, 30; default 24) and Loop. It is NOT real time from the pod: a frame is about 50 MB over RunPod's proxy. "Cache sequence" downloads and decodes the frames in order (two requests at most, abortable, "n of total cached") into memory as 1920-wide RGBA (about 8 MB each, 600 MB at most; a sequence too long to cache whole says so and fetches the rest as the playhead reaches it), and Play starts the caching by itself. The clock (`src/utils/playback.js`) never skips a frame: if the next one is not cached it holds on the shown frame ("Buffering frame n") and continues from the arrival. Once cached, playback is smooth at the chosen fps (requestAnimationFrame timing, no re-decoding). Any manual step, Escape or a hidden window pauses.
6. **Videos have the same controls.** In the same Outputs viewer a video (mp4, webm, mov, m4v) gets the transport bar: Play/Pause (Space), a scrubber with the buffered range, a timecode mm:ss:ff at the fps selector (the file's own rate is not exposed to the page), frame step (arrows while paused, Shift for ten), speed 0.25x to 2x, Loop, volume and fullscreen, beside Previous/Next file, Open and Download. Seeking uses HTTP Range, which the `podfile://` handler already forwards (206 and Content-Range), so no change in `electron/` was needed. A codec the browser engine cannot play (ProRes, some HEVC in .mov: a MediaError 3 or 4, or sound without a picture) shows "This codec cannot be played in the app" with Download and a note to open it in DJV (`/Applications/djv.app`) instead of a black frame; there is no pod-side transcoding.
7. **Empty frames.** The decoder measures each frame from its full-resolution rows (min, max and mean per channel, the fraction of exactly black pixels; about every 3rd pixel of a 4K frame) and flags it `black` or `flat` when every sampled pixel is identical; a clipped frame, or a mostly black one with a real region, is not flagged. A 0-byte file, a truncated one (shorter than its header's data offset plus the image size: "Truncated: n of m bytes"), a header with no pixels and an HTTP 404 ("Missing: the pod has no such file") get the same banner instead of a black canvas. Frames found empty are counted in the viewer ("3 of 25 frames empty", with Previous/Next empty frame buttons; while caching, "n empty frame(s) found so far") and on the sequence tile once they have been loaded or cached; playback goes over them. The viewer shows the current frame's statistics line.
8. **Failures say what happened.** A network or CORS failure of the page's fetch is "Could not reach the pod file: ..." (never a bare "Failed to fetch"); HTTP 404 is "Missing"; other statuses name the status. Inside the app a failed fetch of a `podfile://` address is retried once through the main process (`core.files.read` -> IPC `core:file:read`, only a pod's /view over https), so the viewer still works if the scheme privilege (`corsEnabled` in `electron/main.cjs`) were ever missing. Both main-process pieces need an app restart; the real Electron path is not covered by the Playwright tests (plain Chromium).
9. Tests: `npm run dpx:test` (decoder, frame loader, playback clock, timecode math), `e2e/outputs-dpx.spec.js` and `e2e/video-viewer.spec.js`.

## Amendment (2026-11-17): saved outputs survive a pod stop and an app restart

1. **The problem.** The Outputs button and gallery were built only from the running pod's ComfyUI `/history`, which lives in memory. After the idle stop (or any stop or recreate) the button went dead and the outputs seemed gone, though the files were safe on the network volume.
2. **The record.** The core keeps `output-runs.json` in the app's config folder (`libs/core/src/outputruns.ts`, atomic write: temp file then rename; a corrupt file starts an empty record). One entry per run, keyed by `prompt_id`: workflow (as the Workflows panel names it), `started_at`, `duration_s`, `pod_id`, `pod_name`, `volume_id`, `datacenter`, `recorded_at` and `files` (`filename`, `subfolder`, `type: output`). Only successful runs with at least one `output` file are recorded (temp files are ephemeral); at most 500 files per run (the cap `writers.ts` already applies to a sequence) and the newest 500 runs. No secrets are written.
3. **Where it is recorded** (all best effort, never throwing into the caller): every successful `comfyruns.runs()` read; the end of each graph in a Run (`runflows.ts`); and **before the app stops a pod**: `pods.stop` and the idle watch's `pods.stopper` call `outputruns.beforeStop`, which reads the pod's `/history` once (8 s at most) and records it, then the stop goes on even when the read failed. There is no periodic read: the idle sweep already probes each pod's `/history`, but adding records there would double the traffic for little gain. A pod stopped from RunPod's own console is not covered except by what earlier reads saw.
4. **Why the volume is the key.** The files are on the shared network volume, not on the pod. A run matches a pod by `pod_id` or by `volume_id` (`outputs.saved({ pod_id, volume_id })`; MCP `get_comfy_runs` with `saved: true`), so a pod on the same volume lists the same runs, including those of pods since deleted. `PodStatus.volume_id` carries the pod's `networkVolumeId`.
5. **Card and gallery.** The Outputs button is enabled when the live history has runs with files or saved runs match the pod or its volume. The list merges both, newest first; a run in both is the live one. A run only in the record carries a "saved" badge.
6. **The limit: viewing needs a running pod on the same volume.** ComfyUI serves the files (`/view`), so the gallery uses this pod when it runs, else another running pod on the same volume. With none it still lists the runs and file names, says "Start a pod on <volume> to view these files", and disables open, preview and download. Files are never read from the volume directly.
7. Tests: `libs/core/tests/outputruns.test.ts`, the MCP test for `saved: true`, `e2e/outputs-saved.spec.js`.

**Amendment 2026-11-17 (ADR-045):** the limit in point 6 no longer holds when the RunPod S3 keys are set: the Outputs button is enabled for any pod with a network volume, the gallery lists the volume's `comfy-shared/output/` by folder, and files open through `s3file://` with no pod running. See ADR-045. DPX sequence tiles also show a cached preview of the first frame (ADR-045, point 9).

- **Buffering several frames at once (2026-11-17):** Lucas: 'can we buffer multiple frames at once?'. The DPX viewer's cache fetched two frames at a time; it now fetches 4 by default with a *Frames at once* choice (1, 2, 4, 6, 8, remembered in `dpx.viewer.streams`), and `createFrameLoader` has `setConcurrency`. The frame the playhead waits for still goes first in the queue; the rest are worked in order from the playhead. More streams are faster on a fast link and cost about 50 MB of memory per frame in flight.

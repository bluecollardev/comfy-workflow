# ADR-048: Rendered sequences: mp4 proxies of DPX frames, on the pod or on this PC, kept on the volume and on this PC

**Date:** 2026-11-19
**Status:** Accepted and built (core, IPC, MCP, the `localfile://` protocol). Tested with fakes (no pod, no ffmpeg, no aws); not yet tried against a real pod or the real ffmpeg. The `localfile://` protocol needs an app restart.
**Context from:** Lucas ("render the DPX files into the sequences we can play in the DPX modal ... build on the pods and then the outputs can be synced to local", "we want these to persist", "also have a local preview mechanism, two adapters, one for on pod and one for local, as a fallback", "show an error message if no ffmpeg installed and advise user to homebrew it").
**Extends:** ADR-037 (Run workflows and the Outputs window), ADR-045 (outputs sources), ADR-046 (Auto sync). See also ADR-049 (the Previews modal and the preview cache), ADR-046 (Auto sync pulls `output/`, so proxies arrive by the same-size skip), ADR-037.

## Context

An OCIOWrite DPX frame is about 50 MB. The DPX viewer decodes a frame in the page and, to play a sequence, fetches frames one by one over RunPod's proxy (or the volume's S3 API): a few frames per second at best, and the decoded frames live only in the viewer's memory, so a closed window forgets all of it. A person who wants to scrub a shot needs a small, seekable file that stays.

## Decision

**A render makes an H.264 mp4 proxy of a sequence, once, and keeps it.**

1. **On the pod (adapter `pod`).** The RUNNING pod already has the frames on the volume, so nothing big crosses the network. The core runs ONE `ffmpeg` per pod at a time (`nice`; DPX decoding is CPU heavy) over SSH (`podpull.runSsh`) and writes `comfy-shared/output/.proxies/<dir>/<name>_<width>.mp4` (`.part`, then `mv`). The hidden folder is on the shared volume, so a stopped pod's S3 view and the sync both reach it. The finished proxy is then pulled with the existing sync (`syncrun.run`, `paths`, trigger `render:pull`: `sync_parallel` streams, S3 or SSH as the pod allows) to the same relative path under the mapped local ComfyUI-Shared `output/.proxies/`.
2. **On this PC (adapter `local`), the fallback.** It reads the frames already synced to the mapped ComfyUI-Shared `output/<dir>/` (same relative dir and name as on the pod), runs the SAME ffmpeg argument array with a local ffmpeg spawned asynchronously, and writes `<local output>/.proxies/<dir>/<name>_<width>.mp4` through a `.part` file and a rename. No pull (`needsPull` false); a local sequence goes rendered, then done.
3. **One argument builder.** `ffmpegArgs` builds the array for both adapters (they differ only in the paths). The size is `source` by default (the frames' native size, e.g. 3840x2160, NO scaling: only the RGB to YUV matrix is told, BT.709, `format=yuv420p`); 960, 1280 and 1920 remain as downscales (lanczos) for fast playback. Proxy: `-c:v libx264 -preset veryfast -crf 18`. Review: `-preset medium -crf 14 -pix_fmt yuv420p` (an .mp4, `+faststart`), or ProRes 422 HQ (`prores_ks -profile:v 3 -pix_fmt yuv422p10le -vendor apl0`, a .mov). Timing is frame-exact: a fractional rate is the rational form (`-framerate 24000/1001` for 23.976, 30000/1001, 60000/1001), never a decimal. Progress is parsed from `-progress pipe:1` (`frame=N`) by one shared parser.
4. **Choosing: `where` is `auto` (default), `pod` or `local`** on `plan` and `start`. Auto is the pod when it runs with SSH, else this PC when its check is ok, else a refusal that names BOTH reasons. An explicit `pod` or `local` fails with that adapter's own reason. With auto and the pod chosen, a sequence the pod cannot read (its folder or first frame is missing there) but that is present locally is rendered locally, per sequence; `where` is recorded per sequence in the status. `pod_id` is required only for `pod`; `local` works with no pod. `pulled` is only for pod renders.
5. **Missing ffmpeg.** The local adapter looks for ffmpeg on `PATH`, then `/opt/homebrew/bin/ffmpeg`, `/usr/local/bin/ffmpeg`, `/usr/bin/ffmpeg` (an Electron app has a minimal `PATH`). It NEVER installs or downloads anything. When it is missing the reason (in `plan().adapters[]`, in the 400 of `start`, in a sequence's error) is: "ffmpeg is not installed on this PC. Install it with Homebrew: brew install ffmpeg (Homebrew itself: https://brew.sh), then try again." with `code: 'no_ffmpeg'` and `install_hint: 'brew install ffmpeg'`. A found ffmpeg that does not run (`-version` fails: wrong architecture, killed) gives "ffmpeg was found at <path> but did not run: <first line>" with `code: 'ffmpeg_broken'`. A hit is cached; a miss or a broken one is looked at again after 30 s, so installing it and retrying needs no restart.
6. **Persistence.** On the volume, under `output/.proxies/` (it survives the pod and is the source for any other machine). On this PC, under the mapped `output/.proxies/` (it survives a restart). `clearLocal` deletes ONLY files inside that local folder (a symlink is unlinked, never followed); there is no volume-side delete. Finished render jobs are kept in a small index (`renders.json`, the newest 20).
7. **Resumable.** A proxy that exists with the same width (the width is in the file name) and is newer than the sequence's last frame is skipped, so a re-run does nothing (a skipped pod proxy is still pulled if it is not here). Frame gaps are counted first (a `find` on the pod, a `readdir` here, in chunks with a yield): they are a warning and the contiguous run from `first` is rendered. A sequence whose first frame is missing fails with a clear message. One failing sequence does not stop the next. fps: the request's, else the number between underscores in the name (12 to 120, e.g. `_23.976_`), else 24.
8. **Cancel** aborts the SSH (or kills the local child) and, for the pod, runs a second SSH call that kills the ffmpeg by its pid file and removes the `.part`; locally the `.part` is removed.
9. **Playing the local file: `localfile://`.** A read-only protocol in `electron/main.cjs` (GET and HEAD, Range, privileged: stream, fetch, CORS) serves a proxy as `localfile://p/<url-encoded path under output/.proxies>`. The core's pure guard `renders.resolveProxyFile` decides: only a plain `.mp4` inside the mapped local `output/.proxies/`; `..`, absolute, backslash, control characters, any other extension, a symlink, or a path whose real path leaves the folder are refused. `renders.proxies()` says where each proxy is: on the volume (an S3 listing of its folder by prefix, cached 60 s, works with the pod stopped) and on this PC (a stat), with the `local_url`.
10. **Safety.** Every path goes to the pod as ONE quoted shell word (`q`: single quotes, each embedded quote closed and reopened) in a script on stdin, never concatenated; file names with spaces, quotes, `;`, `$()` and backticks stay data (tested through real `bash`). A name may not contain `/`, `\`, `%` or control characters; a folder may not contain `..` and is never absolute. The local adapter refuses a proxy path that resolves outside `<local output>/.proxies`.
11. **Integration.** One History entry per job (`job: 'render'`: counts, files, bytes, width and the adapters used, e.g. `(pod+local)`); the pull is a normal sync run, so its own History entry carries `trigger: 'render:pull'` and it shows in the sync run registry (Queue > Syncs). One journal batch event for `output/.proxies/<dir>/` per pod-rendered sequence (best effort). When Auto sync is on for the pod, its same-size skip keeps a proxy from being pulled twice (a concurrent pull of the same file by both is possible and harmless: both end with the same bytes).
12. **MCP.** `render_sequences { action: plan | start | status | cancel | proxies, pod_id?, sequences?, width?, fps?, pull?, where?, job_id?, items?, volume_id? }` (ADR-028 parity; `clearLocal` is window-only). IPC `renders.plan | start | status | cancel | proxies | clearLocal`. No named yes: the pod is already running and billed, as with pressing Sync. `status` answers from memory.

**Colour (shared/governance/policy/colour.md).** The policy: plates are DPX 2.0 BE, RGB 10-bit packed, printing density; Cineon log to linear is stated on every Read node, "never guessed"; "the DPX header is reported next to it". This app therefore applies NO colour transform (the in-app viewer, `src/utils/dpx.js`, applies none either: the OCIOWrite files are display-referred, "Gamma 2.6 P3-D65 - Display"), reads the header (transfer, colorimetric, bit depth, packing, size) from the first frame, and records it: in the sidecar and, for a review, as `colour:` lines in DELIVERY.md together with what ffmpeg was told ("no colour transform applied", only the BT.709 RGB to YUV matrix; primaries and transfer are NOT tagged, because that would be a guess). A REVIEW is refused when the header says printing density, linear, logarithmic, Z or ADX (or cannot be read): a review file made with a guessed conversion would look wrong, and the policy forbids guessing. A quick proxy is still made (it is a preview, like the viewer).

## Consequences and limits
- Rendering needs a running pod with SSH, or the frames already on this PC (sync the outputs first) and a working local ffmpeg.
- The proxy is a plain H.264 preview, not the master. Its size is the source size by default (4K encodes are slower and larger); 960, 1280 and 1920 are downscales.
- The proxies sit in a hidden folder (`output/.proxies`) of the shared volume and of the local output; the volume browsers hide dot folders. They cost volume space and, when pulled, one sync of a few tens of MB each. The reconciler lists them with the rest of `output/`.
- The `localfile://` protocol needs an app restart to exist.
- A render holds the pod's CPU; it runs one ffmpeg at a time per pod and one render job at a time per pod (and one at a time on this PC).

## Governance fit (amendment 2026-11-19)
Binc's rules and what they mean here. Sources: `docs/CHUNKING.md` (chunks write frames by number into ONE folder), `shared/governance/policy/` (`project_v002`/`v006`, `served-names.md`, `naming.md`, `colour.md`, `agent-permissions.md`) and Binc's `04_TRACKER/deliverables.csv` (read-only mirror, never written).
- **Frames keep their names.** A render only READS the frames; it never renames or renumbers them and never writes into the sequence folder. Proxies go to `output/.proxies/`, reviews to `output/deliver/`.
- **Stitched = one full-length file per COMPLETE shot sequence.** Because chunks write by frame number into one folder, a sequence rendered in frame order is the stitched video. A sequence is complete when its frame numbers are contiguous from `first` to `last`. An incomplete sequence is REFUSED by default (state `incomplete`, "Incomplete: frames 101-150 are missing (N gaps)", at most the first 10 ranges named, both adapters); `allow_partial` (proxy only) renders the contiguous run from `first` as `<name>_<width>_partial.mp4`. The full-length name is never written for an incomplete sequence, so an incomplete one never passes as whole. Files named like the sequence that do not fit the pattern, and frames of an unusual size, are reported as warnings, not hidden. `plan()` returns `complete` and `missing` per sequence.
- **Two kinds, `kind: 'proxy' | 'review'`.**
  - `proxy` (default): the quick-play file under the hidden `output/.proxies/`; its sidecar says `kind: 'proxy'` and makes no claim about delivery.
  - `review`: the stitched review video, which IS a deliverable ("Hero-eye proxy review for sign-off", one per shot in `deliverables.csv`; format and spec 'not set'). It is written to a VISIBLE, VERSIONED folder on the volume, `output/deliver/<shot>/v###/`, as `<shot>_review_mono_v###.mp4` (and, with `prores422hq`, `<shot>_review_master_v###.mov`), per the naming policy `<shot>_<what>_<detail>_v###.<ext>`: lowercase, no uuid or hash. The shot id is the lowercased `^[A-Za-z]+-\d+[a-z]?` prefix of the sequence name, else the folder's last segment. **Versions only go up:** the version is the next free `v###` (listed on the pod or here and on the volume), created with a plain `mkdir` that fails if it exists (then the next number is tried), so an existing version is never overwritten, moved or deleted: every run is a new version ("nothing is overwritten"). A review needs `approved_by` (400 "A review video needs the name of who says yes"; a named yes, like `autosync.set`); `allow_partial` is rejected for a review; the incomplete sequence is refused.
- **DELIVERY.md** in each version folder (policy: what changed, what was measured): the source sequence and folder, the frame range and count, fps, size, codec(s), tool and adapter, the source of the frames; the frame count rendered against expected, the decoded count from `ffprobe -count_frames` (a mismatch FAILS the render and removes the file), duration, bytes and sha256 of each file (streamed asynchronously locally, `sha256sum` on the pod), the colour lines; who said yes and when; the state line "Ready for Binc's review. Sending to the client is Binc's; this app never sends."; and the spec line "Spec is not set in deliverables.csv; rendered at the source resolution <W>x<H>, <codec>, <fps> fps (review of the full sequence)". It is written atomically (a temp file, then a rename).
- **The sidecar.** Next to every file (`<file>.meta.json`, atomic): `kind` (`proxy` or `review`), source dir and name, first, last, frames, complete, partial, fps, width and height, the adapter, the ffmpeg arguments and version, rendered_at, app version, the total size of the source frames, the colour record, and for a review shot, version, approver, codec, and the outputs with bytes, sha256 and the decoded frame count. It travels with the file: the pull's `paths` list includes it (a review: the whole version folder, DELIVERY.md too), the same-size skip applies, and `proxies()` reads `complete`, `partial`, `fps`, `frames` and the real size from it (no sidecar: unknown, not an error). `proxies()` also lists `deliverables` per shot: `{ shot, version, file, exists_local, exists_remote, bytes, approved_by, rendered_at, local_url }`.
- **Agents never send.** Nothing here sends anything to the client; the DELIVERY.md says so. **Never under `projects/desktop/`:** the local adapter refuses a mapped folder inside Binc's mirror and `assertNotMirror` guards every local write (tested); the app writes only the volume and the mapped local ComfyUI-Shared.
- **History** records `job: 'render'` with the kind, shot, version, codecs and the approver; the pull is a normal sync run (`render:pull`).
- **Assumption and open questions for Lucas and Binc.** The spec for the sign-off review file is "not set" in `deliverables.csv`; this app renders at the SOURCE resolution (3840x2160), H.264 crf 14 (and optionally ProRes 422 HQ, matching the sample name's PRORES422HQ): what is the real spec? The earlier worry that the "full-length mono MP4 per shot" rule of `project_v002/v006` might be gone in `v007`-`v009` is resolved: `deliverables.csv` lists the review per shot.

## Source resolution, codecs, verification (amendment 2026-11-19)
Lucas: the frames are IMAX 4K (3840x2160 in the sample name), which is the point of DPX, so SOURCE size is the default for both kinds (`width: 'source'`: the size is read from the first frame's DPX header: size, bits, transfer, colorimetric, packing, read from its first 820 bytes with `od` on the pod or an async read locally). The proxy file name carries the size: `<name>_source.mp4` for source, `<name>_<width>.mp4` for a downscale, so the two never collide; `proxies()` and the sidecar report the real width and height. A review has two codecs, `h264` (default, the policy's MP4) and `prores422hq` (a master-quality `.mov` companion in the same `v###` folder: 10-bit 4:2:2; the app cannot play ProRes, and `plan()` and the job `notes` say so); both can be asked for in one run (`codecs`), one pass each, sequentially. `plan()` returns for a review `source: { width, height, bits }` and an honest `estimate`: "slow: expect minutes per 100 frames" at full resolution (the measured rate and time left are shown while it renders); no made-up number. A review pass on the pod runs under `timeout 7200` and `nice`; cancel works; locally the pass has the same 2-hour limit. Needs `ffprobe` (on the pod; next to ffmpeg locally: `brew install ffmpeg` installs both) to verify the frame count; without it the review is not rendered.

## Settings (amendment 2026-11-19)
Lucas: "have settings for each pod with these options". The configuration gets `render: { where, kind, proxy_width, review_width, codecs, fps, pull }` (Default Configuration and a pod's own configuration, the way `auto_sync` was added: defaults, normalise, validate with a 400 naming the field (`render.codecs is a non-empty list of h264, prores422hq`), export and import (Pod defaults section, backup and undo), preview, reset, Recreate carries it, IPC and MCP `get/set/preview` configuration and pod config). It NEVER holds an approver or an `allow_partial` default: a review needs a named yes on each run and partial is chosen per run (the import check refuses both keys). `renders.plan` and `renders.start` use the EFFECTIVE settings (the pod's own, else the Default Configuration, else the defaults; a local-only run, with no `pod_id`, uses the Default Configuration's) for every field the request omits, and `plan()` returns them as `settings`; an explicit request field always wins.

## Conform: clip names and timecode (amendment 2026-11-19)
Context (Binc's EDL note): the EDL is CMX3600, 24 fps non-drop (23.976), record timecode is film timecode starting 01:00:00:00 (the reference first frame is 00:59:57:00). "Name each DPX folder and proxy with the clip name in this EDL, so conform relinks." For archival-077 the EDL names differ from the 17 Nov round: 077a `ARCHIVAL-077_A_FINAL_V03_3840X2160_23.976_PRORES422HQ`, 077b `ARCHIVAL-077_B_FINAL_V03_3840X2160_23.976_PRORES422HQ`, 077c `ARCHIVAL-077_C_FINAL_V02_1920X1080_23.976_PRORES422HQ`. The render output is therefore also a conform file. The app reads `EDL-READ.md` and `MANIFEST.json` nowhere and never touches them.
- **ProRes 422 HQ is the review default** (`render.codecs: ['prores422hq']`; 10-bit 4:2:2 `.mov`, source size, the sample name's own PRORES422HQ); H.264 `.mp4` stays selectable and both can be asked for. The quick PROXY is H.264 always (the app cannot play ProRes); the plan notes say so.
- **File names are the clip name.** The base name of every output is the clip name: by default the sequence `name` (the DPX stem, which already is the EDL clip name), overridable per sequence with `clip_name` (for the 077 case where the EDL names differ from the frames' stem). It is validated (1 to 200 characters; letters, digits `. _ - ` and space; no `/`, `\`, `..`, control characters or NUL; no uuid- or hash-looking token, policy/naming.md; trimmed) with a 400 naming `clip_name`. Outputs: proxy `output/.proxies/<dir>/<clip>.mp4` (source size) or `<clip>_<width>.mp4` (downscale; `_partial` for a partial); review `output/deliver/<shot>/v###/<clip>.mov` and/or `<clip>.mp4` with `<clip>.<ext>.meta.json` and `DELIVERY.md`. This REPLACES the earlier `<shot>_review_mono_v###.mp4` and `<shot>_review_master_v###.mov` names: the version lives in the `v###` folder. The shot id for the folder still comes from the clip name (`archival-077` for `ARCHIVAL-077_A_...`). Several takes of one shot (077a/b/c) rendered in ONE job are separate clips in the SAME `v###` folder: one version per shot per job, not per clip (the first clip creates the folder, the others add to it, and each appends its section to `DELIVERY.md`; an existing version is still never overwritten). The frames and their DPX folders are NEVER renamed or written (served names are identity): only outputs carry the clip name; DELIVERY.md and the sidecar record the clip name, and, for an override, the original stem (`frames_stem`). `proxies()` finds a proxy by its clip name, returns `clip_name`, and lists each review version with its files (`.mov`, `.mp4`).
- **Start timecode for relink.** The first frame's DPX television header holds the time code (SMPTE 268M, a U32 at byte 1664 in the file's byte order, packed BCD HHMMSSFF; the magic number says the byte order). When it is present and valid it is passed as `-timecode HH:MM:SS:FF` to ffmpeg (ProRes and H.264, non-drop, `:`), with the exact rate `24000/1001`. Unset (0 or 0xFFFFFFFF) or invalid values (a digit above 9, hours 24 or more, minutes or seconds 60 or more) mean NO timecode: none is embedded and none is invented; DELIVERY.md says "no timecode in the DPX header". The sidecar records `start_timecode` and `timecode_source`, or `timecode_note`.
- **The 1080p take** (`..._C_FINAL_V02_1920X1080_...`) renders at ITS source size (read from its header): no upscale to 4K.

## A cheap card is enough (amendment 2026-11-19)
ffmpeg (prores_ks, libx264) and the DPX decode are CPU-bound and the GPU is idle, so the pod's vCPU count decides the speed, not its card. `plan()` for a pod render probes it over SSH (`nproc`, `free -m`, `df -Pk` of the output folder; 5 seconds at most; best effort, never throws; absent when it fails) and returns `pod_cpu: { cores, mem_mb, free_gb }`. With fewer than 8 cores a source-size (or 1920) review gets the note "This pod has N vCPUs: a 4K review will be slow (expect minutes per 100 frames). A pod with more cores or On this PC may be faster." `estimate.output_gb` (per sequence and in total) is a rough guess: ProRes 422 HQ at 4K about 5.3 GB per minute of picture at 24 fps (frames/fps/60 times 5.3, scaled by the pixel count), H.264 review about 0.8, the quick proxy about 0.4; free space on the pod (or, for the local adapter, this PC's) below that gives a note, never a refusal; an output above 5 GB with the pull on adds "About X GB: a sync of this size asks for approval (Auto sync) or takes a while." The measured encode rate (frames per second, from the clock on the pod and locally) goes into the sidecar (`render_fps`) and DELIVERY.md; the status still reports the live rate and time left.

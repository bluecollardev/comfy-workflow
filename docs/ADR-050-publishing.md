# ADR-050: Publishing to S3 and Slack

Status: built in the core (2026-11-19), screens by the UI agent. Decided by Lucas: "after outputs are generated, we should have an option to publish ... to S3 and slack", with an app-wide configuration in Settings and an option in the Generate window's Render section.

## Governance frame (read this first)
Publishing sends files outside this PC and posts to a channel. Binc's rules apply: agents never send to the client; any write to Slack needs a named yes; "Slack messaging" is on hold (`shared/governance/policy/agent-permissions.md`). So:

- **Always an explicit act of a person.** Every run carries `approved_by` (non-empty, else 400 "Publishing needs the name of who says yes (approved_by)"), after a **plan the person sees first** (what, where, how big). The only automatic path is the explicit per-run option "publish when the render finishes", which carries the same approver; there is no stored default for sending.
- **The MCP tool is refused without `approved_by` and `confirm: true`**: it returns the plan and sends nothing. An agent cannot set the destination (setting it is a window-only action).
- **The destination should be an internal bucket and channel unless Binc says otherwise.** Lucas confirmed the bucket (2026-11-19: "Panama exchange bucket", prefix `returns/BKK/`), which is the existing Panama exchange bucket of Default Configuration. The Slack side is **not configured** until a person enters the webhook.
- **Lucas must confirm that Binc agrees before the first real Slack post** (Slack messaging is on hold in Binc's permissions page). The Test button is the only thing that posts without a file list, and it needs the person's click (the window asks first); nothing posts on its own.
- **Model weights are never published** (`.safetensors .ckpt .pt .pth .bin .gguf .onnx .pkl`): refused in the plan with that reason, in `run` and in backfill.
- **Secrets stay local.** S3 keys and the webhook live only in the app's `.env` (`PUBLISH_S3_ACCESS_KEY_ID`, `PUBLISH_S3_SECRET_ACCESS_KEY`, `PUBLISH_SLACK_WEBHOOK_URL`), are returned only as a hint (last four), and appear in no log, History entry, error, message or file. The app ships as a DMG from a public repository, so **no default contains a webhook, token, key or channel**; a test checks it.

## Settings (`publish.settings()` / `setSettings()`)
Non-secret fields in `publish.json` (atomic), secrets in the `.env`. `setSettings` keeps a secret that is omitted or empty and `clear: ['s3_keys', 'slack_webhook']` removes it; a text field set to `''` returns to its default. Validation (400 naming the field): bucket 3-63 lower case/digits/dots/hyphens; prefix with no leading `/`, no `..`, at most 200 characters, trailing `/` normalised; region like `us-west-2`; endpoint an https URL (S3-compatible); `presign_hours` 1-168; webhook https on `hooks.slack.com` (tests may allow another host with `PUBLISH_SLACK_HOST_ALLOW`); channel `#name`; `workspace_url` an https URL on `*.slack.com`.

Baked, **non-secret** defaults (`PUBLISH_DEFAULTS`, overridable and clearable): S3 `credentials: 'panama'` (the Panama AWS keys, or the profile, from Settings), `prefix: 'returns/BKK/'`, and, with Panama credentials and no saved bucket, `bucket` and `region` taken from the Panama settings (`panama_bucket`, `panama_region`) so the name exists in one place; Slack `workspace_name: 'Beinghuman'`, `workspace_url: 'https://beinghuman-hq.slack.com'`, `username: 'RunPod Manager'`; the message template; no default target. `settings()` reports `s3.note` / `destination_confirmed`: "Lucas, 2026-11-19: Panama exchange bucket, returns/BKK/" (documentation, not a gate). S3 is *ready* with a bucket and credentials (Panama keys set, or separate keys); Slack is ready only when a webhook is saved, otherwise `problem` says "Add the Incoming Webhook URL for Beinghuman (Slack: Apps > Incoming Webhooks)".

## The flow
`local({dir})` lists one level of the local `output/` (async, links never followed, `..` refused, 2000 entries). `plan({items, targets, message?})` expands folders (async, 20,000 files, yielding every 500), keeps the structure under the prefix (`deliver/<shot>/v###/<clip>.mov` lands at `<prefix>/deliver/<shot>/v###/<clip>.mov`), skips an object already there with the same size (the destination listed by prefix once, not per file), refuses weights and links, names the blockers and renders the Slack preview (`Beinghuman: #channel` and the text). `run` re-plans on the server, uploads with `aws s3 cp` (spawned, up to `sync_parallel` at once, progress from the CLI's `Completed ...` text, a stall timer per progress line and never a total timeout, so multi-GB ProRes files finish), then **only when every upload succeeded** posts ONE Slack message (title, approver, first 10 names and sizes, `...and N more`, total, destination prefix, presigned links for the first 10; the template takes `{approved_by} {count} {size} {dest} {files} {links} {date}`). A Slack failure after good uploads ends as `done_with_warning` and `publish.slack({job_id})` posts again. Jobs are in memory (instant `status`), the last 20 in `publish-jobs.json` without signed links; History gets one `job: publish` entry per run and a `change` entry when settings change (field names, never values). `test({target})`: S3 is read-only (`ls`, then a one-key listing; nothing written), Slack posts "RunPod Manager: test message" only when called; both 10 s.

**Publishing from the volume (2026-11-19).** The Outputs window shows the volume's folders, so the picker can too: `publish.volume({dir})` lists ONE level of the volume's `comfy-shared/output/` over the app's RunPod S3 access (read-only, async, 2000 entries, never recursive), with an `empty` flag per folder from a one-key probe (8 at a time, 3 s each, absent when unknown), so shells with no files can be marked; folder sizes are not computed there, `publish.volumeSize({path})` does it on demand (a recursive listing of that prefix, cached 5 minutes, `volumeSizeCancel` aborts it). `plan` and `run` take items as a string (a path under this PC's `output/`) or `{ where: 'volume', path }` (under the volume's `output/`). A volume item is expanded by prefix, keeps its relative path under the destination prefix, skips same-size objects already there, refuses weights, shows `source: 'volume'` and counts in `streamed_files` / `streamed_bytes`; it is uploaded by the Backfill's streaming path (two piped aws commands with `--expected-size`, at most 3 at a time, no local copy), and local and volume items can be mixed in one run. The Outputs listing (`historyAPI.listOutputs`) carries the same probe as `folder_info: { name: { empty? } }` next to the unchanged `folders` array of names.

**From a render:** `renders.start({..., publish: { targets, message? }})` publishes the finished files once they exist on this PC (a review: the version folder with DELIVERY.md and sidecars; a proxy: the mp4) with the job's `approved_by`, which is then required also for a proxy. A render left on the pod (pull off) is refused: "Pull the renders to this PC first". Never a stored default.

## Backfill: what the outputs already hold
Kyle (2026-11-19): "I can't find a finished shot anywhere ... Upload finished shots to S3 returns/BKK/ as they are ... Naming can be fixed after." Built from ADR-051 section 8, in `publish.ts`; the event emission arrives with ADR-051 phase 1, for now the records are rows in `publish-inventory.json` (`backfilled: true`, `event_time` = the file's modified time, ids a hash of source + path + size, so a second scan duplicates nothing) and History `change` entries per shot.

1. **Scan** (`scan({sources})` then `inventory(job_id)`): read-only, async, by prefix, never the whole volume. Sources: this PC's `output/`; on the volume `comfy-shared/output/`, `comfy-shared/input/pipe_finals/`, `project/90_DELIVERIES/` over the app's RunPod S3 access. Rows: DPX sequences grouped the way the gallery groups them (frame number differs only), shot from `renders.shotOf` (or `deliver/<shot>/`), kind `dpx-sequence | review | proxy | movie | other`, frames, bytes, modified, where (`pc`, `volume`), `in_destination` (ONE listing of the destination), weight flag; plus `by_shot`, totals and `unreadable` (what could not be read and why; a shot with nothing found is "none found", never "delivered").
2. **Plan** (`backfillPlan({rows | all: true, targets, destination_prefix?})`): keys keep the **original names** under `<prefix><shot>/<name>` (a sequence's frames in a folder named for it), same-size skip, weights refused (`all` leaves them out and counts them), the full destination `s3://<bucket>/<prefix>` shown.
3. **Run** (`backfillRun({..., approved_by})`): files on this PC go with `aws s3 cp`; files only on the volume are **streamed through this PC**: `aws s3 cp s3://<runpod-bucket>/<key> -` piped into `aws s3 cp - s3://<dest>/<key> --expected-size <bytes>` (no temp file, nothing buffered, back pressure from the pipe), at most 3 streams, progress by bytes, a stall timer per file; cancel kills both ends. `_inventory_<yyyy-mm-dd>.csv` (shot, name, kind, frames, bytes, modified, where, uploaded yes/no/already) is uploaded **last**, over stdin, next to the files. With Slack as a target ONE status message follows only after everything succeeded: "Outputs inventory and upload: N shots, M files, X GB uploaded to <dest>; as they are, naming to be fixed after", per-shot counts for the first 15 shots and the approver, **never a link**. Needs Lucas's confirmation with Binc before the first real post, like any Slack post.

## Contract
IPC namespace `publish`: `settings, setSettings, test, local, plan, run, status, cancel, slack, backfill(op, o)` (op `scan | inventory | plan | run`). MCP tool `publish` (actions `settings local plan run status cancel slack backfill`); `setSettings` and `test` are window-only (parity map). Tests: `libs/core/tests/publish.test.ts`, `publish-backfill.test.ts`, the render hook in `renders.test.ts`, the MCP rules in `mcp/server.test.mjs`; fakes only (no S3, Slack or RunPod).

## Consequences
Finished work can leave the PC with one named yes and one visible plan, and nothing else can. The cost is that Slack stays off until a person adds a webhook and Binc agrees; S3 works as soon as the Panama keys are set.

## Amendment 2026-11-19: Auto-publish (finished, approved review videos go to the returns folder by themselves)
Lucas: "can we auto upload to Tunnel?" and, choosing the fully automatic option, "do this". Today every publish is a person's explicit act with a name (above). **Auto-publish** is a standing rule that does the upload when its conditions are met, with no click per run. Because Binc's rules say sending anything to the client is Binc's and agents never send, it is **off by default and needs a named standing approval**, and it is built with guards so that only what a person has approved can leave.

**What it publishes (all must hold):**
1. a **Review video** (`output/deliver/<shot>/v###/`: the `.mov`/`.mp4` files, `DELIVERY.md` and the sidecars), never a quick proxy, never a partial (`_partial`) or incomplete sequence;
2. its `DELIVERY.md` and sidecars exist and the colour verdict was `ok` when it was rendered (a review refused for colour never exists);
3. the files are on this PC (the render's pull finished; a pod-only render is not uploaded until it has been pulled);
4. **the shot version is marked approved** by a named person (see below);
5. none of the files is a model weight (always refused), and nothing at the destination has the same size already (the usual skip).

**Approval of a shot version.** A review version is **approved** only by a person: a **Mark approved** action (in the Outputs window's review badge, the Publish window, and the Queue's render card) that records `{ shot, version, approved_by, at }` in `approvals.json` (app config, History `change` entry). It uses the contract's term HUMAN APPROVED (Binc's `hitl-signoff.md`); **Revoke** removes it and cancels a pending auto-publish of that version. A new version (`v002`) is not approved until someone approves it.

**The standing approval.** Turning Auto-publish on in **Settings > Publishing > Auto-publish** requires a name in a field ("Approved by") and a tick "This allows the app to upload approved review videos to <destination> by itself", and records it once (History `change`, shown in the settings as "Approved by <name> on <date>"; turning it off clears it). The ADR records that **Lucas confirms Binc's yes before the first real automatic upload**; until then the setting can be configured and run in **dry-run** only.

**The guards:**
- **Cancel window:** an eligible version is queued, not sent: it appears on the Queue ("Auto-publish: archival-085 v002 uploads in 9:41", **Cancel** and **Publish now**) and in a banner, and uploads when the window (default 10 minutes, 0 to 120, settable) ends. A Cancel, Revoke or Off before then stops it.
- **Daily cap:** at most N automatic uploads per day (default 5, set in settings); beyond it versions wait for the next day or for **Publish now** (a person's explicit click, with a name).
- **Dry-run:** the rule runs, records what it *would* upload (the Queue shows "would upload", History and, if ticked, Slack say so) and sends nothing. The default on first enabling.
- **Slack:** each automatic upload posts one message (shot, version, files, size, destination, "uploaded automatically under the standing approval of <name>"; no links) to the connected channel, as a normal publish with the Slack target ticked.
- **Instant off switch:** a chip in the header ("Auto-publish ON") with an **Off** button; Off cancels everything pending and stops the rule at once; the same call over MCP (`publish` action `autopublish_off`).
- **Audit:** every automatic upload is a History `job: 'publish'` entry with `trigger: 'auto-publish'`, the approver of the shot version, the standing approver, the destination and the counts.
- **Scope:** only the configured destination (the Panama exchange bucket, `returns/BKK/` by default) and never a different prefix; the rule cannot be pointed elsewhere without turning it off and on again.

**Where it lives:** `libs/core/src/autopublish.ts` (the rule, the approvals store, the pending queue with its timer, the daily counter), hooked where a review job finishes and is pulled (`renders.ts`) and on start (to pick up versions approved while the app was closed), IPC `autopublish.*` and MCP `autopublish` (status, settings get, approvals list and mark/revoke, pending list, cancel, publish now, off); the page: the Settings block, the header chip, the Queue entries, the Mark approved actions. Built on `publish.run` (same plan, same weights refusal, same streaming), so nothing new can leave that a manual publish could not.

**Still open (Lucas, Binc, Kyle):** how Tunnel actually receives (does it pull from `returns/BKK/`, or is there another route?); who approves a shot version (Brynley, Binc?); whether the daily cap and cancel window defaults suit; Binc's standing yes.


## Amendment 2026-11-19: transfer adapters (a pod on the volume uploads, S3 to S3)

**Why.** A file that lives only on the RunPod network volume was copied by streaming it through this PC (`aws s3 cp s3://<volume>/... -` piped into `aws s3 cp - s3://<bucket>/...`), about 3 MB/s. RunPod's volume S3 API and AWS are different services, so there is no server-side S3-to-S3 copy. The fast path is a pod in the volume's datacenter, attached to that volume, uploading straight from the mounted volume at datacenter speed.

**Two adapters** (`libs/core/src/publish.ts`):
- `pc`: today's behaviour, unchanged: the two piped `aws` commands through this PC. It now also hashes the bytes that pass, so the file's sha256 is known.
- `pod` ("S3 to S3"): a RUNNING pod already attached to the volume runs, over the app's existing pod SSH runner, a script per file: `sha256sum`, then `curl -T <file>` to a presigned PUT URL. The URLs are made on this PC with the destination's keys (`s3presign.ts`, SigV4 query string, method PUT, only `host` signed, unsigned payload), so no secret key ever reaches the pod. One URL per destination key, made just before that file starts, valid for 1 hour (S3 checks the expiry when the request starts, not when it ends). The URL travels in the script on ssh's stdin and reaches curl as a config on stdin (`-K -`), never as a command-line argument.

**Selection.** Setting `s3.transfer` (Settings > Publishing > Defaults, Auto / Pod / This PC): `auto` (default) uses the pod when it is available, else `pc`; `pod` forces the pod and fails the job with a plain-words reason when it is not available; `pc` forces today's path. Available means all of: a pod is running AND attached to the volume (never one of the app's own pull pods) AND the destination keys are S3 keys saved in the app (an AWS profile cannot presign) AND a probe over SSH (20 s) finds `curl` and `sha256sum`. **Nothing here ever creates, resumes or stops a pod**; spending is a person's named yes (Binc's `agent-permissions.md`). The only RunPod call is reading the pod list (a test pins that).

**Fallback.** In `auto`, if the pod fails one file (curl error, timeout, ssh drop) that file goes through `pc`, once, and the next file tries the pod again. In `pod` there is no fallback: the file fails the job, naming the pod. A file over 5 GiB cannot be a single signed PUT: in `auto` it goes through `pc`, in `pod` it fails with that reason. **Cancel** kills the ssh and then runs `pkill -P <pid>; kill <pid>` on the pod (the pid the script reported), and does not fall back.

**Record.** The job has `adapter` (`pod` or `pc`: what carried the volume files; `pc` when none did), `pod` (its name, when used), `pod_files`, `pc_files`, and `files[]` (first 200: `path`, `adapter`, `sha256`, and `shot` for a backfill). The Publish window and the Queue card say "via pod <name>" or "via this PC". History's job line ends with the counts.

**A presigned URL is a credential.** It is never logged, and never in History, an error, the job view or the stored job file: `redact()` strikes the live URLs, any `X-Amz-Signature/Credential` text and the Panama keys from everything the pod says before it is kept (a test makes the pod echo the URL back and scans the view, the job file and History).

**Limits.** Progress for a pod file moves when the file completes (curl runs silent); a pod that stops mid-transfer drops the ssh, which is a failure of that file (so, in `auto`, a retry of it through this PC). Not tested against a real pod or real S3: the tests use fakes for ssh, aws and spawn.

# ADR-050: Publishing to S3 and Slack

Status: built in the core (2026-11-19), screens by the UI agent. Decided by Lucas: "after outputs are generated, we should have an option to publish ... to S3 and slack", with an app-wide configuration in Settings and an option in the Generate window's Render section.

## Governance frame (read this first)
Publishing sends files outside this PC and posts to a channel. Binc's rules apply: agents never send to the client; any write to Slack needs a named yes; "Slack messaging" is on hold (`shared/governance/policy/agent-permissions.md`). So:

- **Always an explicit act of a person.** Every run carries `approved_by` (non-empty, else 400 "Publishing needs the name of who says yes (approved_by)"), after a **plan the person sees first** (what, where, how big). The only automatic path is the explicit per-run option "publish when the render finishes", which carries the same approver; there is no stored default for sending.
- **The MCP tool is refused without `approved_by` and `confirm: true`**: it returns the plan and sends nothing. An agent cannot set the destination (setting it is a window-only action).
- **The destination should be an internal bucket and channel unless Binc says otherwise.** Lucas confirmed the bucket (2026-11-19: "Panama exchange bucket", prefix `returns/BKK/`), which is the existing Panama exchange bucket of Default Configuration. The Slack side is **not configured** until a person enters the webhook.
- **Lucas must confirm that Binc agrees before the first real Slack post** (Slack messaging is on hold in Binc's permissions page). The Test button is the only thing that posts without a file list, and it needs the person's click (the window asks first); nothing posts on its own.
- **Model weights are never published** (`.safetensors .ckpt .pt .pth .bin .gguf .onnx .pkl`): refused in the plan with that reason, in `run` and in backfill.
- **Secrets stay local.** S3 keys and the webhook live only in the app's `.env` (`PUBLISH_S3_ACCESS_KEY_ID`, `PUBLISH_S3_SECRET_ACCESS_KEY`, `PUBLISH_SLACK_WEBHOOK_URL`), are returned only as a hint (last four), and appear in no log, History entry, error, message or file. The app ships as a DMG from a public repository, so **no default contains a webhook, token, key or channel**; a test checks it.

## Settings (`publish.settings()` / `setSettings()`)
Non-secret fields in `publish.json` (atomic), secrets in the `.env`. `setSettings` keeps a secret that is omitted or empty and `clear: ['s3_keys', 'slack_webhook']` removes it; a text field set to `''` returns to its default. Validation (400 naming the field): bucket 3-63 lower case/digits/dots/hyphens; prefix with no leading `/`, no `..`, at most 200 characters, trailing `/` normalised; region like `us-west-2`; endpoint an https URL (S3-compatible); `presign_hours` 1-168; webhook https on `hooks.slack.com` (tests may allow another host with `PUBLISH_SLACK_HOST_ALLOW`); channel `#name`; `workspace_url` an https URL on `*.slack.com`.

Baked, **non-secret** defaults (`PUBLISH_DEFAULTS`, overridable and clearable): S3 `credentials: 'panama'` (the Panama AWS keys, or the profile, from Settings), `prefix: 'returns/BKK/'`, and, with Panama credentials and no saved bucket, `bucket` and `region` taken from the Panama settings (`panama_bucket`, `panama_region`) so the name exists in one place; Slack `workspace_name: 'Beinghuman'`, `workspace_url: 'https://beinghuman-hq.slack.com'`, `username: 'RunPod Manager'`; the message template; no default target. `settings()` reports `s3.note` / `destination_confirmed`: "Lucas, 2026-11-19: Panama exchange bucket, returns/BKK/" (documentation, not a gate). S3 is *ready* with a bucket and credentials (Panama keys set, or separate keys); Slack is ready only when a webhook is saved, otherwise `problem` says "Add the Incoming Webhook URL for Beinghuman (Slack: Apps > Incoming Webhooks)".

## The flow
`local({dir})` lists one level of the local `output/` (async, links never followed, `..` refused, 2000 entries). `plan({items, targets, message?})` expands folders (async, 20,000 files, yielding every 500), keeps the structure under the prefix (`deliver/<shot>/v###/<clip>.mov` lands at `<prefix>/deliver/<shot>/v###/<clip>.mov`), skips an object already there with the same size (the destination listed by prefix once, not per file), refuses weights and links, names the blockers and renders the Slack preview (`Beinghuman: #channel` and the text). `run` re-plans on the server, uploads with `aws s3 cp` (spawned, up to `sync_parallel` at once, progress from the CLI's `Completed ...` text, a stall timer per progress line and never a total timeout, so multi-GB ProRes files finish), then **only when every upload succeeded** posts ONE Slack message (title, approver, first 10 names and sizes, `...and N more`, total, destination prefix, presigned links for the first 10; the template takes `{approved_by} {count} {size} {dest} {files} {links} {date}`). A Slack failure after good uploads ends as `done_with_warning` and `publish.slack({job_id})` posts again. Jobs are in memory (instant `status`), the last 20 in `publish-jobs.json` without signed links; History gets one `job: publish` entry per run and a `change` entry when settings change (field names, never values). `test({target})`: S3 is read-only (`ls`, then a one-key listing; nothing written), Slack posts "RunPod Manager: test message" only when called; both 10 s.

**Publishing from the volume (2026-11-19).** The Outputs window shows the volume's folders, so the picker can too: `publish.volume({dir})` lists ONE level of the volume's `comfy-shared/output/` over the app's RunPod S3 access (read-only, async, 2000 entries, never recursive), with an `empty` flag per folder from a one-key probe (8 at a time, 3 s each, absent when unknown), so shells with no files can be marked; folder sizes are not computed there, `publish.volumeSize({path})` does it on demand (a recursive listing of that prefix, cached 5 minutes, `volumeSizeCancel` aborts it). `plan` and `run` take items as a string (a path under this PC's `output/`) or `{ where: 'volume', path }` (under the volume's `output/`). A volume item is expanded by prefix, keeps its relative path under the destination prefix, skips same-size objects already there, refuses weights, shows `source: 'volume'` and counts in `streamed_files` / `streamed_bytes`; it is uploaded by the Backfill's streaming path (two piped aws commands with `--expected-size`, at most 3 at a time, no local copy), and local and volume items can be mixed in one run. The Outputs listing (`historyAPI.listOutputs`) carries the same probe as `folder_info: { name: { empty? } }` next to the unchanged `folders` array of names.

**From a render:** `renders.start({..., publish: { targets, message? }})` publishes the finished files once they exist on this PC (a review: the version folder with DELIVERY.md and sidecars; a proxy: the mp4) with the job's `approved_by`, which is then required also for a proxy. A render left on the pod (pull off) is refused: "Pull the renders to this PC first". Never a stored default.

## Backfill: what the outputs already hold
Kyle (2026-11-19): "I can't find a finished shot anywhere ... Upload finished shots to S3 returns/BKK/ as they are ... Naming can be fixed after." Built from ADR-051 section 8, in `publish.ts`; the event emission arrives with ADR-051 phase 1, for now the records are rows in `publish-inventory.json` (`backfilled: true`, `event_time` = the file's modified time, ids a hash of source + path + size, so a second scan duplicates nothing) and History `change` entries per shot.

1. **Scan** (`scan({sources})` then `inventory(job_id)`): read-only, async, by prefix, never the whole volume. Sources: this PC's `output/`; on the volume `comfy-shared/output/`, `comfy-shared/input/pipe_finals/`, `project/90_DELIVERIES/` over the app's RunPod S3 access. Rows: DPX sequences grouped the way the gallery groups them (frame number differs only), shot from `renders.shotOf` (or `deliver/<shot>/`), kind `dpx-sequence | review | proxy | movie | other`, frames, bytes, modified, where (`pc`, `volume`), `in_destination` (ONE listing of the destination), weight flag; plus `by_shot`, totals and `unreadable` (what could not be read and why; a shot with nothing found is "none found", never "delivered").
2. **Plan** (`backfillPlan({rows | all: true, targets, destination_prefix?})`): keys keep the **original names** under `<prefix><shot>/<name>` (a sequence's frames in a folder named for it), same-size skip, weights refused (`all` leaves them out and counts them), the full destination `s3://<bucket>/<prefix>` shown.
3. **Run** (`backfillRun({..., approved_by})`): files on this PC go with `aws s3 cp`; files only on the volume are **streamed through this PC**: `aws s3 cp s3://<runpod-bucket>/<key> -` piped into `aws s3 cp - s3://<dest>/<key> --expected-size <bytes>` (no temp file, nothing buffered, back pressure from the pipe), at most 3 streams, progress by bytes, a stall timer per file; cancel kills both ends. `_inventory_<yyyy-mm-dd>.csv` (shot, name, kind, frames, bytes, modified, where, uploaded yes/no/already) is uploaded **last**, over stdin, next to the files. With Slack as a target ONE status message follows only after everything succeeded: "Outputs inventory and upload: N shots, M files, X GB uploaded to <dest>; as they are, naming to be fixed after", per-shot counts for the first 15 shots and the approver, **never a link**. Needs Lucas's confirmation with Binc before the first real post, like any Slack post.

## Contract
IPC namespace `publish`: `settings, setSettings, test, local, plan, run, status, cancel, slack, backfill(op, o)` (op `scan | inventory | plan | run`). MCP tool `publish` (actions `settings local plan run status cancel slack backfill`); `setSettings` and `test` are window-only (parity map). Tests: `libs/core/tests/publish.test.ts`, `publish-backfill.test.ts`, the render hook in `renders.test.ts`, the MCP rules in `mcp/server.test.mjs`; fakes only (no S3, Slack or RunPod).

## Consequences
Finished work can leave the PC with one named yes and one visible plan, and nothing else can. The cost is that Slack stays off until a person adds a webhook and Binc agrees; S3 works as soon as the Panama keys are set.

## Amendment 2026-11-19: Auto-publish (finished, approved review videos go to the returns folder by themselves)
Lucas: "can we auto upload to Tunnel?" and, choosing the fully automatic option, "do this". Today every publish is a person's explicit act with a name (above). **Auto-publish** is a standing rule that does the upload when its conditions are met, with no click per run. Because Binc's rules say sending anything to the client is Binc's and agents never send, it is **off by default and needs a named standing approval**, and it is built with guards so that only what a person has approved can leave.

**What it publishes (all must hold):**
1. a **Review video** (`output/deliver/<shot>/v###/`: the `.mov`/`.mp4` files, `DELIVERY.md` and the sidecars), never a quick proxy, never a partial (`_partial`) or incomplete sequence;
2. its `DELIVERY.md` and sidecars exist and the colour verdict was `ok` when it was rendered (a review refused for colour never exists);
3. the files are on this PC (the render's pull finished; a pod-only render is not uploaded until it has been pulled);
4. **the shot version is marked approved** by a named person (see below);
5. none of the files is a model weight (always refused), and nothing at the destination has the same size already (the usual skip).

**Approval of a shot version.** A review version is **approved** only by a person: a **Mark approved** action (in the Outputs window's review badge, the Publish window, and the Queue's render card) that records `{ shot, version, approved_by, at }` in `approvals.json` (app config, History `change` entry). It uses the contract's term HUMAN APPROVED (Binc's `hitl-signoff.md`); **Revoke** removes it and cancels a pending auto-publish of that version. A new version (`v002`) is not approved until someone approves it.

**The standing approval.** Turning Auto-publish on in **Settings > Publishing > Auto-publish** requires a name in a field ("Approved by") and a tick "This allows the app to upload approved review videos to <destination> by itself", and records it once (History `change`, shown in the settings as "Approved by <name> on <date>"; turning it off clears it). **Binc's yes is given** (Lucas, 2026-11-19: "binc says yes"; relayed, and recorded here and in the standing approval's name and date when it is turned on). The app still starts in **dry-run** the first time and going live is a named act, as a safe habit, not because anything is pending.

**The guards:**
- **Cancel window:** an eligible version is queued, not sent: it appears on the Queue ("Auto-publish: archival-085 v002 uploads in 9:41", **Cancel** and **Publish now**) and in a banner, and uploads when the window (default 10 minutes, 0 to 120, settable) ends. A Cancel, Revoke or Off before then stops it.
- **Daily cap (optional, OFF by default; Lucas, 2026-11-19: "remove cap for now"):** when switched on, at most N automatic uploads of review versions per local day (1 to 50); beyond it versions wait for the next day or for **Publish now** (a person's explicit click, with a name). With no cap (the default) nothing limits the number of approved versions uploaded in a day: the cancel window, approvals, dry-run and the instant Off are then the brakes.
- **Dry-run:** the rule runs, records what it *would* upload (the Queue shows "would upload", History and, if ticked, Slack say so) and sends nothing. The default on first enabling.
- **Slack:** each automatic upload posts one message (shot, version, files, size, destination, "uploaded automatically under the standing approval of <name>", with the links, the preview frame and the volume source of every Slack post: see "Links in every Slack post") to the connected channel, as a normal publish with the Slack target ticked.
- **Instant off switch:** a chip in the header ("Auto-publish ON") with an **Off** button; Off cancels everything pending and stops the rule at once; the same call over MCP (`publish` action `autopublish_off`).
- **Audit:** every automatic upload is a History `job: 'publish'` entry with `trigger: 'auto-publish'`, the approver of the shot version, the standing approver, the destination and the counts.
- **Scope:** only the configured destination (the Panama exchange bucket, `returns/BKK/` by default) and never a different prefix; the rule cannot be pointed elsewhere without turning it off and on again.

**Where it lives:** `libs/core/src/autopublish.ts` (the rule, the approvals store, the pending queue with its timer, the daily counter), hooked where a review job finishes and is pulled (`renders.ts`) and on start (to pick up versions approved while the app was closed), IPC `autopublish.*` and MCP `autopublish` (status, settings get, approvals list and mark/revoke, pending list, cancel, publish now, off); the page: the Settings block, the header chip, the Queue entries, the Mark approved actions. Built on `publish.run` (same plan, same weights refusal, same streaming), so nothing new can leave that a manual publish could not.

**Decided (Lucas, 2026-11-19):** Binc's standing yes is given. Who approves a shot version is **outside this workflow and the team's to coordinate** (Lucas: "irregardless of our workflow, that's up to them to coordinate"): the app enforces no list of approvers and only records the name typed at Mark approved, with the time. How Tunnel receives files: **no separate route**; the destination is the configured one (the Panama exchange bucket, `returns/BKK/`), changeable only in Settings. The cancel window defaults to 10 minutes and is settable; the daily cap is off by default (settable).

### Auto-publish targets: S3, Slack, Tunnel (Lucas, 2026-11-19)

### Auto-publish is a configuration setting (build note)
The settings live in the Default Configuration (`auto_publish` in `mounts.json`), app-wide: a pod's own configuration never keeps it. Defaults: off, dry run, 10 minutes, **no daily cap** (`daily_cap: null`; a number is 1 to 50, `0` or empty means no limit; the day's count is always recorded so a cap switched on mid-day counts what went out), targets `{ s3: true, slack: false, tunnel: false }` (Tunnel is refused until it exists; Slack needs S3; one of the two must be on while enabled). **Safety:** the standing approval and `enabled: true` never travel: an import forces `enabled: false`, `dry_run: true`, drops `standing` and `targets.tunnel` (the window, cap and S3/Slack choice are imported; the plan says "Auto-publish will be imported turned OFF"), an export marks its `standing` as informational, a backup and Undo restore this PC's exact earlier state, and MCP can neither enable it, go live, set the standing approval nor change the targets (403). Only `autopublish.setSettings` (the window) creates a standing approval. The runtime state stays outside the configuration: `approvals.json`, `autopublish-state.json` (uploaded versions, today's count, what was uploading). The configuration is re-read when its file changes, so a change applies at the next tick. Uploads run one at a time. Two choices differ from the first sketch: changes of these settings do not write an import backup (they would push real import backups out of the ten kept), and each is a History `change` naming fields and targets, never a value that is a secret.

### Dry run is optional, and a setting (Lucas, 2026-11-19: "optional plz ... in settings")
Starting in dry run is a recommendation, not a requirement. The `auto_publish` block carries **`dry_run_first: boolean`** (default `true`; Settings > Publishing > Auto-publish: "Start in dry run when turned on"):
- **Ticked (default):** turning Auto-publish on starts in dry run (nothing is sent; the Queue shows "would upload"); going live is a later, deliberate step.
- **Unticked:** turning Auto-publish on goes **live at once**, with the same name and "I understand" in the one confirm.
- **Going live later** (unticking Dry run on a running rule) no longer asks for a second name: the standing approval already holds one; it asks for a plain confirm ("The next approved version will really be uploaded"). The 400 for going live without a standing approval stays.

The cancel window, approvals, targets and the instant Off apply either way.



### Slack previews and the source on the volume (2026-11-19)
Every post to Slack (a manual publish, the backfill status message and Auto-publish, which calls `publish.run`) can carry two extras, each a setting under `slack` (shown by `publish.settings()` and the MCP `publish` tool, both default on): **`preview_frame`** and **`volume_source`**.
- **Preview frame.** When S3 and Slack are both targets, the first three distinct clips of the run that are on this PC give one image each: a `.mov`/`.mp4` its first frame, a DPX sequence its lowest-numbered frame, made by `ffmpeg -y -i <file> -frames:v 1 -vf scale=1280:-2 -q:v 3 <jpg>` (arguments as an array, the ffmpeg the renders find, 30 s each, a plain scale with no colour transform like the proxies). The jpg is a temp file under the app's cache folder, removed after the run, and goes up next to the files as `<prefix>/<shot>/<clip>_preview.jpg` (same-size skip). It is listed apart (`plan.previews`, `job.previews`, flagged `preview: true`) and never counts in the files of the run. The Slack payload keeps `text` as the fallback and adds `blocks`: the usual summary first, then for each preview a line (shot, file, size) and an `image` block whose URL is an expiring presigned link (`presign_hours`, https, under 3000 characters), then the volume source; at most 50 blocks, 3000 characters a text. No ffmpeg, a failed frame, a failed upload or a failed presign leave a quiet warning in the job (`warnings`) and the post is the text alone; a file that is only on the volume gives no preview in this version ("Preview unavailable", once). No signed URL is written to History, the jobs file or a log. `plan.slack.preview_frames` and the preview text say what the post will carry.
- **Source on the volume.** RunPod's S3 API does not accept presigned URLs and the volume is private, so there is no clickable link to a file. When the published files came from the volume (a `{ where: 'volume', path }` item, a backfill row that is there, or a file this PC pulled from a pod render, whose sidecar says `adapter: pod`) the post adds a section "Source on the volume: <name> (<datacenter>) · `comfy-shared/output/<path>/` (first three folders, +N more) · RunPod console: Storage" (the generic Storage page, there is no per-volume URL) and a context block with a copy-paste `aws s3 ls s3://<volume id>/<folder> --endpoint-url https://s3api-<datacenter lower>.runpod.io --region <datacenter lower>`. The name and datacenter come from the volume list (cached 5 minutes); with no record only the id and path show, with no command. Never a key or a secret. A purely local file, or the setting off, omits the block.


### Links in every Slack post (2026-11-19, Lucas: "we need links")
All three kinds of message (a manual publish, the backfill status, Auto-publish) carry links, each a setting under `slack`: **`folder_link`** (default on): a link per destination folder (the first five), `https://s3.console.aws.amazon.com/s3/buckets/<bucket>?prefix=<prefix>/<shot>/<version>/&region=<region>` (the prefix URL-encoded, the slashes kept), labelled "Folder: <shot> v002" with the S3 address as text; it is permanent, never signed, and opens only for people with access to the bucket (no folder link for a custom S3 endpoint, which has no AWS console page). **`file_links`** (default on) with **`file_link_count`** (1 to 25, default 10): expiring presigned URLs (`aws s3 presign`, `presign_hours`, at most 7 days) for the first N files, shown "expires <date>"; the sidecars, `DELIVERY.md` and the preview images get none; more files than N say "+N more (the folder link covers them)". Anyone who has the message can open a file link until it expires, so the links go only to the connected channel. A presign that fails leaves that one link out with a job warning. The links sit in their own blocks (split under Slack's 3000 characters a text, 50 blocks) and in the fallback `text`; the header block never holds them. The default template gained `{folders}` next to `{links}`; a template with neither still gets the links appended. `plan.slack.links` ({ folder, files, expires_at }) and the plan preview ("With a link to the destination folder and links to the first 10 files, expiring <date>") say what will be there. **No signed URL or console link is written to History, the jobs file or a log.** Auto-publish keeps its wording ("uploaded automatically under the standing approval of <name>"), the backfill its inventory summary; both add the same links, previews and source block.

### Publishing on the Queue (2026-11-19, Lucas: "publishing is a que events yes?" ... "yes")
Every manual publish and every backfill upload is a **job on the Queue** (ADR-051 section 9), in a **Publishing** section of the Queue window: progress (files, bytes, rate, the current file), the target badges (S3, Slack), the phases (Uploading, Posting to Slack), who approved it, Cancel while it runs, Re-post when only the Slack message failed, the warnings (for example no preview frame), and when done the summary and the links (folder links, file links with their expiry, the preview image). Running publishes count in the Queue badge, and closing the Publish window never cancels one. Auto-publish keeps its own section (pending entries with countdowns) and is not repeated here. Their start, finish, warning and failure become events when the event system (ADR-051) is built.



### The render hook and the configuration (2026-11-19)
`render.publish { s3, slack }` in the configuration only **pre-ticks** the Generate window's "Publish to S3 / Post to Slack when done"; it is never a send. `renders.start` publishes only when the request carries an explicit `publish: { targets }` AND `approved_by`, and only from files that are on this PC (so the same window also needs "Sync the renders to this PC", now off by default, or a local render). A start without the field publishes nothing, so an agent or a stale client cannot publish by configuration alone.

### The BKK return layout, the manifest and the Tunnel proxy (Kyle, 2026-11-19)
Kyle (through his agent) answered what the returns need; it is the spec for what this app uploads to `returns/BKK/`. **Write access is done** (the panama key can upload to `returns/`; it cannot delete; `rounds/` and `masters/` stay read-only). Spec, as stated:
- **Layout:** `returns/BKK/<round>/<shot>/<files>`, with **`RETURN-MANIFEST.json` (schema `bh-return-1`) at the round root**, as in the earlier BKK returns; an inventory CSV at the round root is fine. A round name looks like `qc_2026-11-02_r01`, `depth-105_h3_iterations_2026-11-03_r01`.
- **The deliverable:** 4K, 16-bit RGB DPX, the EDL range with no handles, **named with the V11 EDL clip names** (a DPX folder per clip: `<shot>/<clip>/<clip>.<frame>.dpx`).
- **Proxies:** H.264, 1920x1080, 23.976, **same name, frame count and start timecode as the DPX**, no burn-ins, **Rec.709**; H.264 because Tunnel's Avid wants it (not ProRes); stored as `<shot>/<clip>.mp4`.
- **Timecode:** the **source** timecode, not the record timecode: it equals the DPX header and the EDL source-in; most files start at `00:00:00:00`, the stills at `01:00:00:00`. (**Superseded below: there is no default timecode.** The order is the sequence field, the DPX header, the EDL's source-in, else stop and flag.)
- **Per shot, now:** finished shots are uploaded as they are finished, not in a full batch; the round's manifest is rewritten after each shot (read the existing one, replace or add that shot's items, upload it last).
- Names stay as they are until Jon decides (cgi-090 shot 2, carter-reframe).

**What the app does (v1.6.2):**
1. **Round and layout.** Publishing to the returns needs a **round name** (400 without it; `^[A-Za-z0-9._-]{3,100}$`; a list of existing rounds from the bucket is offered) and uses the layout `bkk-return` (the default when the prefix is under `returns/BKK/`): DPX sequences to `<round>/<shot>/<clip>/<clip>.<frame>.dpx`, proxies and reviews to `<round>/<shot>/<clip>.<ext>`, other files to `<round>/<shot>/<file>`; the shot comes from the clip name (`archival-077` from `ARCHIVAL-077_A_FINAL_V03_…`). **Clip names:** each sequence can be renamed for the upload (the EDL name); frames on disk are never renamed; the manifest records the original name.
2. **`RETURN-MANIFEST.json` (bh-return-1).** `{ schema_version, round, returned_by (the approver), returned_at (ISO with the local offset), pod { provider, pod_id, gpu, hours, cost_usd, paid_by, provider_api_calls } (from the render or volume job when known, else "n/a"), items: [ { shot, element (the take: A, B, main…), input_final { delivered_name, sha256 }, graph { name, sha256, returned_path }, outputs: [ { path (relative to the round root), role (dpx, proxy-h264, review, graph, sidecar), sha256, bytes, and for media width, height, fps ("24000/1001"), frames, codec, bit_depth, colour { working_space } } ], measures { kind, frames, notes } } ] }`. **A sha256 is computed for every uploaded file** (a streamed hash while reading, async, chunked; a volume-streamed file is hashed in the stream). The manifest is uploaded **last**, merged with the existing one in the round; the inventory CSV goes to the round root too.

### Auto-publish sources: this PC and/or the volume (2026-11-19, Lucas: "auto publish should scan volume and / or local pc add to default configuration")
Auto-publish used to read only the local `output/deliver/<shot>/<version>/` on this PC, so a Queue with outputs on the volume stayed empty and said nothing. It now has **two sources**, each a setting in the **Default Configuration** (`auto_publish.sources`):
- **`local`** (default on): the review folders on this PC, as before.
- **`volume`** (default on): the same layout on the RunPod volume, `comfy-shared/output/deliver/<shot>/<version>/`, listed through the S3 API (one browse job at a time, ADR-050's rule), each review's sidecar read as a small object. A version is the same version whether it is found locally or on the volume: when both have it, **this PC wins** (no second upload); an entry records where it came from. A volume review is published by streaming volume to bucket (the existing path), never downloaded first, and its source DPX frames stream the same way when `include_dpx` is on.
- **`volume_scan_minutes`** (default 5, 1 to 120): the volume is listed on its own, slower cycle than the 5-second local tick; a **Scan now** button runs it at once. Listings are cached, capped and abortable like the Outputs listing, and the scan only looks at `deliver/` (never the whole tree).
- **Nothing else changes:** a version still needs its approval record (Binc says yes) and a valid sidecar, the standing approval, the cancel window, the targets, the optional dry run and the optional daily cap. Scanning more places never uploads more without the approval.
- **The status says what it watches:** `watching { local: {root, reviews}, volume: {id, reviews, scanned_at, scanning}, approved, eligible, queued, skipped[], summary }`, shown on the Queue's Auto-publish section and in the settings block ("Watching this PC (0 reviews) and the volume (12 reviews, scanned 2 minutes ago): none approved yet"). A source turned off says so; both off is refused (400 "Choose at least one place to watch").
- **Imports and the MCP:** an import keeps the preferences; the MCP may change `sources` and `volume_scan_minutes` (they only widen what is looked at; the approver and the standing approval stay window-only).
- **Global only (Lucas: "global is fine"):** `sources` and `volume_scan_minutes` belong to the Default Configuration like the rest of the `auto_publish` block; a pod's own configuration never carries them (stripped on save and import, as `outputs` is).

### Auto-publish can generate the outputs too (2026-11-19, Lucas: "auto publish should also auto generate outputs (this can be an option in settings too)")
Auto-publish only sends what exists: review videos in `deliver/<shot>/<version>/`. The step before it, rendering a finished DPX sequence into that review (and the Tunnel proxy), was a manual Generate. It becomes an **option of Auto-publish**, `auto_publish.generate`, in the Default Configuration (global only, like the rest of the block):
- **`enabled`** (default **off**), **`where`** (`local` default | `pod`), **`preset`** (`review` default | `tunnel`), **`max_per_day`** (default 20, null for none), **`settle_minutes`** (default 5).

### Build notes for v1.6.2 (what the core does, where it differs from the sketches above)
- **Shots are child jobs.** A publish run (manual, Auto-publish, backfill) is a PARENT with one CHILD per shot (`children[]`: `id` `<job>:<n>`, `parent_id`, `shot`, `clip`, `state` queued/uploading/done/failed/cancelled, `files`, `files_done`, `bytes`, `bytes_done`, `rate`, `current`, `skipped`, `error?`, `warnings`, `approved_by`, `slack`, `sha256`), plus `counts`, `streams` and, on the job, `kind: 'publish'` and `trigger: 'manual' | 'backfill' | 'auto-publish'`. Children run one at a time, or up to `streams` (at most sync_parallel) at once; each uploads, hashes, merges its own items into the round's manifest and, with `slack.per_shot` (default on for the BKK return, off otherwise), posts its own Slack message; with it off the parent posts one message after every shot is done. One failed shot does not stop the others and adds nothing to the manifest; `publish.retry(child_id)` tries it alone and skips what is already in the bucket with the same size; `publish.cancel(id)` takes a job id (all children not done) or a child id. The backfill's children are progress only (no per-shot manifest, retry or cancel).
- **The manifest** is written after EACH child, behind a per-round async lock (so parallel children and parallel runs never lose each other's items); the job reports `manifest { updated, shots, path, error? }`, `sha256_count` and `results[]` (path, bytes, sha256; the first 1,000). `input_final.sha256` is the sha256 of the lines `<frame file name> <frame sha256>` of the clip in name order (a digest of the sequence), or the movie's own sha256 when there are no frames. A manifest already in the round that cannot be read is a 409 and nothing is overwritten.
- **Render + publish pipeline.** `renders.start({ publish: { targets, round?, clip_names?, message? } })` starts one publish run per rendered sequence as soon as THAT sequence's files are on this PC (after its own pull); `job.publish.job_ids` lists them.
- **Auto-publish sources and generation.** `auto_publish.sources { local, volume }` and `volume_scan_minutes` (Default Configuration only) make it watch this PC's `output/deliver/` and/or the volume's `comfy-shared/output/deliver/` (listed one level at a time, 500 versions and 5,000 objects at most, every 5 minutes, "Scan now" = `autopublish.scanVolume`); this PC wins when both have a version; `status().watching` is `{ local, volume, approved, eligible, queued, uploaded_today, skipped[], summary }`. `auto_publish.generate` (off by default) renders NEW finished sequences (frames newer than the switch-on, unchanged for `settle_minutes`) with `renders.start({ trigger: 'auto-publish', skip_existing: true })`, locally or on an already running pod, within `max_per_day`; it never approves and never publishes; `status().generate` reports `generating`, `generated_today`, `waiting_to_settle[]` and `failed[]`. A pod needs the approver's name in the same save.

### Auto-publish is a pipeline: generate, then publish to the BH S3 bucket, with no per-version approval (2026-11-19, Lucas: "auto publish should simply generate and publish to BH s3")
The per-version approval record ("Binc says yes", one entry per shot and version) made Auto-publish wait for a click that nobody was making, and the Queue stayed empty. That contradicts Lucas's earlier ruling ("binc says yes", "who approves a shot version is up to them to coordinate"). Decision:
- **The standing approval is the named yes.** With `auto_publish.enabled` and a standing approval (the person who turned it on, with the date), every **eligible** review is published; no entry per version is needed.
- **`auto_publish.require_approval`** (Default Configuration, global only, default **false**): when true, the old behaviour returns (only versions with an approval record go). Existing approval records stay valid either way.
- **A hold replaces the approval as the safety valve:** `revoke` (a hold) on a shot version stops it from ever being auto-published, with or without `require_approval`; holds are listed and can be released.
- **The pipeline reads as three steps in the UI:** 1 Generate the reviews (this PC, or a running pod; auto-generate), 2 Publish to the **BH S3 bucket** (the configured destination: the Panama exchange bucket, `returns/BKK/<round>/`, with the manifest), 3 Post to Slack. Each step is a tick; the standing approval, the window before upload (cancel window), the dry run, the optional daily cap and the weights guard are unchanged.
- **Eligible** still means: a review with a valid sidecar (kind review, not partial, colour not refused), found on this PC or the volume, not already at the destination, not held, and clear of the EDL flags for a Tunnel/return round. Imports still force Auto-publish off.

### Graph failures and fail fast (v1.7.0)
Every failed graph is one record in `failures.jsonl` (stage, node, message, missing models with where they belong on the volume, recovery, retryable, attempt; no credential or URL). `run_pod_workflows` fails a load or validation error at once (no polling) and never retries it; a transient cause (pod stopped, network, 5xx) is retried at most twice, 5 then 20 minutes later and after the other graphs; three graphs in a row failing for the same cause pause the dispatch once (History and Slack). A graph has a hard limit (3x its last successful run, else 2 hours) and a stall limit (neither queued nor running on the pod for 10 minutes; ComfyUI gives no progress over HTTP, so this is the signal). The same failure fields are on `get_comfy_runs` (`failure`), `get_comfy_logs` (`problems`), `queue_list` (`failure`), `chunked_job`, render and publish status, and the round preflight (`problems`). Jobs of other processes are listed through `jobs-running.json` (`running_jobs`, `external: true`).

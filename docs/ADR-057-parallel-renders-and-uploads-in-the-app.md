# ADR-057: Long renders and uploads run in the app, in parallel, and survive a restart

**Date:** 2026-11-21 (Bangkok time)
**Status:** Accepted. **Built and merged:** 1 (renders in the app), 2 (re-attach, `e2d5c38`), 6 (settings block, `be976da`). **Being built on branches (not merged):** 3 (frame ranges and split, `feature/run-ranges-split`), 5 (pod choice, parallel uploads, byte progress, `feature/publish-pod-choice-parallel`). **Not built:** 7 (wiring `dpx_fix` into the pipeline), 9 (scope for Auto-generate and Auto-publish).
**Context from:** the Tunnel V11 delivery of 21 November (`docs/CANALV2-TUNNEL-V11-PRODUCTION-PLAN.md` sections 18 to 24, `docs/CANALV2-TUNNEL-V11-DELIVERY-REPORT-2026-11-20.md`), ADR-038 (queue), ADR-050 (publishing), ADR-055 (delivery integrity), ADR-056 (memory-safe runs).

## 1. What happened (the evidence)
- **A render loop died with its host.** The chunked render of backhalf-b ran as a loop inside the stdio MCP server (the process that serves Claude Code's tool calls). A dropped connection at 16:34 restarted that server and ended the loop. The chunk in flight kept running on the pod; nothing collected it.
- **Jobs the app cannot see.** Another session of Lucas's rendered CGI-072 head, PHOTOREAL-013 hadal and CGI-072 backhalf-c with a hand script (`chunkrun.mjs`, client `chunkrun-mac`) straight into a pod's ComfyUI. Those renders were not in Queue, History or `running_jobs`, and the app's own runs of the same elements would have duplicated them.
- **One element uses one pod.** A chunked run submits its chunks one after another on one pod, so five elements need five pods and more pods do not make one element faster. At 1x RTX PRO 4500 (57.7 GiB RAM) a delivered frame cost about 51 s (chunks of 11 frames with an 8-frame pad each side, so 27 frames processed for 11 delivered); sunlight did not fit even 5 frames on that card.
- **RAM comes with the GPU count** (2x RTX PRO 4500 = 116.4 GiB), but a pod created with `like_pod_id` ignores the requested GPU count and came up as 1x; one 2x pod also reported 55.9 GiB.
- **Uploads took the busiest pod and ran one at a time.** `auto` picks the first running pod on the volume (here the other session's pod: about 6.5 MB/s), a job sends its groups in sequence, and a second job waits. The Queue showed `141 of 266 files · 0 B of 0 B` for an upload started outside the app.
- **Auto-generate and the preview batch hit render pods.** Auto-generate and `Load all previews` read or render on whichever pod is running, including one with a render queue (previews timed out with `The file did not arrive in time`).

## 2. Decisions
1. **Long renders run through the app's own queue** (Import Round, queue tasks, the app's MCP endpoint 127.0.0.1:8765), never as a loop in the stdio MCP server and never by a hand script. A hand-script render is accepted as a source only after the same checks (frame count against the PDF, contiguous numbering, same size, then `dpx_fix`, then publish), and nobody starts a run on a pod whose ComfyUI `/queue` shows a prompt from another client.
2. **A chunked run is saved as a record and adopted after a restart** (built: `chunkrecord.ts`, `reattach.ts`, ADR-056 section 7). The record holds the pod, the plan and each chunk's state; the app adopts a record whose owner is gone, waits for a running prompt, counts finished chunks, resubmits a lost one once, continues from the first chunk not run, and never rewrites a frame (a chunk owns its start number). A run started by code without records is not adoptable: it becomes `interrupted`.
3. **One element can render on several pods at once** (building): an optional `range: { first, last }` per path clamps the planner; output numbering stays absolute, so ranges from different runs fill one folder without overlap; the 8-frame pad applies at the range edges as inside a run; a split helper (`run_split`, task option `split: N`) creates the ranges, one run per pod, retries a failed range once and checks the union is exactly `0..N-1`. Pods are only ours: `exclude_pod_ids` keeps it off other sessions' and foreign pods.
4. **Renders use 2x pods and create them with an explicit GPU count.** 2x allows chunks of about 50 frames (pad overhead about 1.3 times, not 2.5), estimated at about 32 s per delivered frame (the 1x figure of 51 s is measured; the 2x figure is not yet). A 1x pod is used only for small elements. The account limit is 16 GPUs; our own pods stay within five or six at a time.
5. **Uploads choose their pod and run in parallel** (building): `auto` ranks running pods that pass the SSH probe by load (no ComfyUI prompt running first, then lower RAM use, then more GPUs), accepts `pods` and `exclude_pod_ids`, spreads a job's shot groups over up to `parallel_pods` pods (default 2), fails a group over once, and never sends a file over 5 GB through this PC. The shared running-jobs record carries bytes, rate and current file, so the app shows real bytes for a job started in another process. `transfer: pod` stays a person's setting.
6. **The Prepare For Delivery settings are a configuration block** (built: `delivery_prepare`, ADR-055 section 12): output folder, colour code, gamma, frame-rate and timecode sources, frame position, skip-existing. Export, import, backup and undo carry it; the approved-by name is never exported or imported. `dpx_fix` and the window read it as their defaults; a plan flag still blocks a run.
7. **`dpx_fix` is wired into Auto-publish (built 2026-11-21, `002f218`, merged to `develop`, live after the next restart; ADR-055 section 13).** With `include_dpx` on, Auto-publish runs `dpx_fix` itself from the `delivery_prepare` settings (plan values verbatim, the standing approval's person, a running pod chosen by the pod ranking), uploads the corrected copies from `output/_delivery_v11/<clip>/`, and holds the whole review with the reason when the plan has a flag, the frame count differs, there is no approver or pod, or the fix fails; a sequence not in the EDL goes as video only. The setting `auto_publish.fix_dpx` (default true, window checkbox `Fix DPX Before Upload`) turns it off, and then no DPX are included. `dpx_fix` is still not run after Import Round or queue runs. Before this was live, `include_dpx` stays off (turned off at 18:48 on 21 November). Earlier wording: **`dpx_fix` stayed a deliberate step.** It is run from the Prepare For Delivery settings (plan values verbatim, approved by a named person, stop on a flag) before every publish of DPX. Wiring it after Import Round, and refusing to publish unfixed DPX from Auto-publish, is proposed, not built. Until then **Auto-publish must not upload DPX** (`include_dpx` off), because it would send the original frames with the wrong header.
8. **f23 is deferred** (Lucas, 2026-11-21): 633 frames take about 5.6 hours on one 2x pod; it is finished later with decision 3 (three ranges, about 2 hours) or as one overnight run. The real round holds 35 of 36 until then.
9. **Scope before Auto-publish goes live** (built 2026-11-21, `9d97fcb`, merged; setting `auto_publish.scope` = `edl` default | `all`, ADR-050 amendment; live after the next restart; tonight the pending list is still reviewed by hand until then): Auto-publish and Auto-generate also see work that is not ours (assembly `NOT_RELEASED` runs, map-066, chasmfastia2, mono_v018 sequences). Going live waits until the pending list is reviewed and every entry that is not one of the 36 is cancelled or excluded (the EDL check, or `require_approval`); Auto-generate and the preview batch do not use a pod that has a render queue (S3 route or an idle pod).
10. **Process.** Merges to `develop` on 21 November after v1.7.2 went in without the full gate at Lucas's instruction (outputs grouping and paging, frame previews and the filmstrip, chunk-run merging and incomplete-sequence hiding, manifest issues, the settings block, re-attach, and the branches above); v1.7.2 itself passed the full gate. The gate runs before the next release.

## 3. Consequences
- A restart no longer loses a run that was started after decision 2; the renders started before it (top, landing, sunlight on 21 November) still do, so the app is restarted only after they finish.
- Elements finish in about one pod-hour per 100 frames on 2x instead of per 50 on 1x, and one element can use several pods; the cost stays about the same (pod-hours add up the same).
- The Queue and History see every render the app starts; renders started elsewhere stay invisible, which is why decision 1 forbids them.

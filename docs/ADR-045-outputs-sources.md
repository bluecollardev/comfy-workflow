# ADR-045: output sources: a pod's history, the saved record, and the network volume over S3

**Date:** 2026-11-17
**Status:** Built 2026-11-17 (uncommitted on `feature/volumes-v2-fallback`). Tested with fakes; the listing and a ranged read were checked once, read-only, against the real Shared volume (section "Live check").
**Context from:** Lucas ("if outputs are on s3, CanalV2-base-graphs-v001-v27-a100 outputs button is greyed out why can't we have an adapter pattern for this. add adapter for s3 to read outputs directly from volume without having a started pod").
**Extends:** ADR-037 (the Outputs gallery and the saved record), ADR-044 (the read-only S3 listing the Import Round agent built). In the spirit of ADR-017 (adapters).

## Context

The Outputs button of a pod card was enabled only from the pod's live ComfyUI history or from the app's saved record (ADR-037). A stopped pod whose runs were not recorded showed a greyed-out button, though the files sit on the shared network volume under `comfy-shared/output/` and RunPod's S3 API can read that volume with no pod (ADR-041, ADR-044). Viewing the files, even for recorded runs, needed a running pod on the volume.

## Decision

1. **An output source is a small interface** (`libs/core/src/outputsources.ts`): `{ id, name, hint, available(ctx), list(ctx, opts), address(file, ctx) }`. `ctx` is `{ pod_id?, volume_id?, shot?, round? }`. `list` answers `{ runs: OutputRun[], folders, prefix, capped, total }`; a run is `{ prompt_id, workflow, started_at, duration_s?, files: [{ filename, subfolder, type, bytes?, modified? }], source }`, the shape the gallery already consumes. `address` is the fetchable base of the source's files: a pod's https address, or `s3file://<volume>`.
2. **Three sources are registered**, in precedence order:
   - `pod-history`: the running pod's own ComfyUI history (`comfyruns.ts`), unchanged;
   - `saved`: the record the app keeps past a stop (`outputruns.ts`), unchanged;
   - `volume-s3`: new. The files under `comfy-shared/output/` of the pod's network volume (or an explicit `volume_id`, else the Shared or default volume), over RunPod's S3 API. No pod, no spend.
3. **Merging** (`mergeRuns`, `listOutputs`): newest first, each run keeps its `source` tag. The same run in two sources shows once, **live over saved over volume**: by `prompt_id` for pod and saved; a volume folder counts as the run of a pod or saved run that wrote any file into it. A source that cannot answer is reported in `sources` with its reason and never stops the others.
4. **`volume-s3` browses by prefix, lazily.** Listing the whole output tree (125 GB, tens of thousands of objects) takes minutes, so level 1 lists only the top-level folders (`proxy_v004`, `proxy_v005`, ...), and a prefix lists what is under it. Up to two levels deep it is one level (`aws s3 ls`, folders as `PRE`); from `output/<top>/<shot>/` down it lists everything under the prefix, so the leaf folders appear as runs. A **run** is a folder that holds files (a frame sequence, a video folder); `started_at` is the newest `LastModified` in it; files carry size and time; the gallery's existing `galleryTiles` makes a DPX sequence one tile. At most 3000 files per listing (`capped`, with the total: the window says "Showing the first N of M"). Listings are cached 90 s (`volumeround.listPrefix`, built on the Import Round's `podpull.listVolumeKeys`; the same availability check). With no prefix and a pod that has a Shot, the listing starts in `output/*/<shot>/` (the pod's round's folder first, then the highest-sorted) when it exists, else at the root.
5. **Unavailable says why and starts nothing:** no S3 keys, a datacenter without the S3 API, or no volume. `available` returns the reason; the window explains "Set the RunPod S3 keys in Default Configuration to browse a volume's outputs without a pod" with a button that opens Default Configuration at the key fields.
6. **Serving bytes with no pod: the `s3file://<volume>/<url-encoded key>` protocol** (`electron/main.cjs`, next to `podfile://`, same privileges: standard, secure, fetch, CORS, stream, bypass CSP). The page's `viewUrl` builds it from a file whose base is `s3file://<volume>`; the key is `comfy-shared/output/<subfolder>/<filename>`. The handler asks the core (`outputsources.signGet`) to guard and sign the read, fetches it in the main process with the `Range` header, and answers 200 or 206 with `Content-Range`, so video seeking and the DPX viewer work. `core:file:read`, `core:file:download` and the zip accept `s3file://` too.
7. **The guard.** Only `GET` and `HEAD` (405 otherwise). The key must start with `comfy-shared/output/`, name a file (no trailing slash), contain no `.`/`..`/empty segment, no backslash or control character, no query or fragment, at most 1024 bytes; the host must be a volume the app knows (the configuration's Shared and default volumes, the saved runs' volumes, and any volume a listing already reached). Anything else is a **403**, before any signature is made. Without S3 keys the answer is a 409 that names the keys. An S3 error is passed on as its status, never its body (it may echo the request), and an S3 403 is shown as 502 so a 403 always means "refused by the guard".
8. **Secrets.** The S3 keys are read where the core already reads them (`settings.lookup('RUNPOD_S3_ACCESS_KEY' / 'RUNPOD_S3_SECRET_KEY')`) and stay in the main process. The signature (SigV4 `Authorization` header, `libs/core/src/s3presign.ts`) is made per request and sent to RunPod only; it is not in a response, an error message or a log. The page never sees the keys.

9. **Previews of DPX sequences** (`src/utils/thumbs.js`, `SequenceThumb.vue`). A sequence tile shows its FIRST frame, decoded to about 320 px and kept as a small WebP data URL. Lazy and bounded, because a frame is about 50 MB: only a tile that is on screen (IntersectionObserver) asks; one sequence at a time; **nothing loads by itself**: a preview already in the cache shows at once (no fetch), every other tile shows **Load preview**, and the modal header has **Load all previews** (Lucas, 2026-11-17: automatic loading on scroll was tried in v1.3.0 and undone in v1.3.1, 'let's click the button, this causes too much loading'; `AUTO_CAP` is `0`, a number or `Infinity` turns automatic loading back on); a tile that scrolls away while it loads aborts its fetch, so the cost is one frame at a time for what was asked for. A finished thumbnail is cached in IndexedDB (`pod-manager-thumbs`) by volume id (else pod id) + folder + first file name, **not** by the address that served it, so a running pod, a stopped pod's saved record and the S3 volume source share one thumbnail and it is fetched and decoded once ever; the file's size and time are kept in the record and a size that is now known and differs makes it a miss. A blank first frame's verdict (black or flat) is stored beside it, so the Empty badge needs no fetch. At most 500 are kept (the oldest evicted); the Outputs modal header shows `N previews cached` with **Clear preview cache** (it only means they are downloaded again). A cache hit costs no cap slot and no network. Persistence: the renderer's IndexedDB lives in the Electron user-data folder, so it survives restarts; it is keyed by the page's origin, so the dev server (`http://localhost:5173`) and the packaged app (`file://`) keep separate caches, and the no-spend Electron specs launch with a temporary `--user-data-dir`, so theirs is wiped on purpose. The base is whatever the files resolve to (a running pod's `podfile://`, else `s3file://`); with none, the tile keeps its icon and the message about starting a pod or setting the S3 keys. An empty first frame (black, flat, 0 bytes, truncated, missing; the viewer's statistics) shows an **Empty frame** badge and is not cached; nothing spins forever: first byte 30 s, the whole thumbnail 120 s, a list call 45 s (`window.__THUMB_TIMEOUTS__` shortens them in tests), then a retry icon with the reason in its title: no answer in time, the pod does not serve the file (404: is it stopped?), set the S3 keys (409), or *Restart the app to enable previews from the volume* (the running app predates `s3file://` or the new IPC calls). With no usable base (no running pod on the volume, no S3 keys) the tile shows an eye-slash icon titled *Start a pod on <volume> or set the S3 keys to see previews* and requests nothing. The run list never waits on the volume: if the listing fails or times out, the saved and live runs stay and an inline error line shows. Storage that throws is ignored.

### Why a signed header and not a presigned URL

The first design presigned a query-authenticated GET URL (`presign()` in `s3presign.ts` is still there, tested against AWS's documented query example). Against the real volume RunPod's S3 answers it with **401 "missing Authorization header"**: it does not accept query authentication. The read is therefore signed with an `Authorization` header (`signHeaders()`, tested against AWS's documented header example for a ranged GET Object) and the main process sends the headers itself. Same keys, same guard, same process boundary.

## MCP

`list_outputs { pod_id?, volume_id?, source?, prefix?, fresh? }` (docs/MCP-ENDPOINTS.md): all sources or one; read-only. IPC `history.outputSources`, `history.listOutputs`.

## Limits

- **Listing is by prefix only.** The whole tree is never listed. A prefix whose subtree is large (a delivery folder with thousands of frames) still lists everything under it from the third level down, `aws s3 ls` pages 1000 objects a call, and only then are 3000 shown: open a deeper folder.
- **Viewing needs the S3 keys** (or a running pod on the volume, which is preferred when there is one). Without keys the saved runs are only listed, as before.
- **A volume listing times are the CLI's local time** (`aws s3 ls` prints them without a zone); they order runs and show as shown.
- **No deletes, no writes, ever.** Every call to the S3 API from this source is `s3 ls` or a signed GET/HEAD; a test asserts it. Nothing is renamed or moved (Binc's rules).
- A saved or pod run's files are read from the volume by the same relative path ComfyUI used (`subfolder`/`filename` under the output folder), which is the layout the pods mount.

## Live check (2026-11-17, read-only, this Mac, the app's own keys)

`comfy-shared/output/proxy_v004/archival-080/` listed in about 2 s: five `archival-080_<a..e>_v004_dpx16` folders, 26 files each (25 frames and a sidecar), 130 objects. One signed `GET` with `Range: bytes=0-0` of the first frame answered **206** with `Content-Range: bytes 0-0/49768064`. The presigned-URL variant answered 401 (above).
